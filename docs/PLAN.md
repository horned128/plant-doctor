# Plant Doctor 統合実行

## 0. この文書の位置づけ

この文書は、**ProtoPedia「植物ストレスを診て水やりするエッジAIテラリウム」の企画原文を唯一の正**として、
実装順序、実機での到達条件を1つに統合した実行計画です。

作るものの定義は企画が決めます。本書は「誰が・どの順で・どう実装し、何をもって完了とするか」を決めます。

### 0.1 文書の優先関係

| 文書 | 本書との関係 |
| --- | --- |
| **ProtoPedia企画原文** | **正。** 何を作るか、どう表示するか、どのデモを成立させるかはここが決める。 |
| [ML63Q2557ファームウェア設計](firmware/ml63q2557/ARCHITECTURE.md) | 現在のソース構造・実行モデルの記述として有効。層構造と責務分担は守る。 |
| [コーディングルール](firmware/CODING_RULES.md) | **有効。** ユーザーコードの書式規約。違反はレビューで差し戻す。 |
| [ピン接続](PIN_CONNECTIONS.md) | **有効。** 実配線の記述。変更時は同文書も更新する。 |
| [VS Code開発環境](VSCODE_SETUP.md) | **有効。** ビルド・書き込み・デバッグ手順。 |

**競合時の扱い**：M2〜M6は「到達点」、P0〜P8は「そこへ到達する実装手順」です。
両者の作業順序や詳細が競合する場合は、より細粒度の**Pトラック／タスクカードと§7の実行順序を優先**します。

### 0.2 現在地

- `PlantDoctor`：電源自己保持、10 msタイマ、LED、LCD、スイッチ、エラー状態まで実装済み。
- `SensorManager`：SEN0206、BME280、SEN0228、SEN0193、SEN0204を1秒周期で取得し、LCDの表示中ページを1秒周期で更新しながら、3ページを5秒周期で切り替えて表示する実装を完了。
- `PumpControl`：DT-EBML63Q2557のSSR出力（OUT0 / P66）ハードウェア制御、最大駆動時間タイマ（2.0秒）、クールダウン（3.0秒）、液面センサ連携、SW4による手動給水・停止トリガー、LCD表示フィードバック、エラー時緊急停止を実装完了。
- `PlantAi`、`PlantLog`は、インターフェースまたはスタブ段階。
- Solist-AIの学習・推論ライブラリは現CMakeビルドに未接続。
- I2CのLCDとSEN0206/BME280/SEN0228はCN3上の同一バスを共有する。

本書では、各段階の「コードがある」ことではなく、**A分類なら自動検証、B分類なら実機の数値基準まで満たすこと**を完了条件とします。

### 0.3 配置方針

- ML63Q2557固有のビルド設定、ドライバ、アプリは`firmware/ml63q2557/`に置く。
- 今後別MCUを追加する場合は`firmware/<mcu>/`を追加し、アプリの仕様・ログ形式・テスト基準は必要になってから共通化する。
- README以外の設計・配線・試験・本計画は`docs/`に置く。

### 0.4 エージェントの読み順

エージェントは §1 → §2 → §3 → §5 を読み、§7で実行順序を確認したうえで、担当タスクカード（§8）と §9 を読んでから着手してください。

### 1.2 表示値の集合（企画の表示例から確定）

`Status`に現れる値：

## 2. 作業開始前の前提条件

### 2.1 リポジトリ取得

`external/CMSIS`はGit submoduleです。未取得だとCMakeが`FATAL_ERROR`で停止します。

```bash
git clone --recurse-submodules <repository-url>
cd plant-doctor
git submodule update --init --recursive
test -f firmware/ml63q2557/external/CMSIS/CMSIS/Core/Include/core_cm0plus.h
```

最後の`test`が失敗する状態ではビルドできません。ZIP展開したツリーはsubmoduleが空なので、
必ず実クローンから作業してください。

### 2.2 エージェントが自己検証に使える手段

```bash
# ARMクロスビルド（CIと同じ経路）
cd firmware/ml63q2557
cmake --preset debug   && cmake --build --preset debug
cmake --preset release && cmake --build --preset release
arm-none-eabi-size build/release/PlantDoctor.elf

# ホスト単体テスト（P0-1で新設。それまで存在しない）
cmake -S tests/host -B build/host && cmake --build build/host && ctest --test-dir build/host
```

必要なツール：`gcc-arm-none-eabi`、`libnewlib-arm-none-eabi`、`ninja-build`、`cmake`、ホスト`gcc`。
未導入の環境が多いので、CIと同じ手順で導入します。

```bash
sudo apt-get update
sudo apt-get install -y gcc-arm-none-eabi libnewlib-arm-none-eabi ninja-build cmake
```

導入できない環境では、**検証者はCIになります。** その場合はPR本文に
「ローカルでビルド検証できず、CIの結果に依存する」と明記し、CIが緑になったことを確認してから
レビューへ回してください。**ビルドを試さずに「ビルドが通る」と書かないこと。**

### 2.3 エージェントが持たないもの

**MCU-Link、実機、I2Cセンサ、SSR、ポンプ、USBシリアル、テラリウム、植物に一切アクセスできません。**
この制約が §3 の作業分類の根拠です。

## 3. 作業の分類 — 「エージェントが自分で検証できるか」

すべてのタスクカードは次の3分類のいずれかを持ちます。

| 分類        | 意味                           | 完了の定義                                                                                                        |
| ----------- | ------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| **A** | エージェント完結               | ARMビルドが通り、ホスト単体テストが通る。これで完了。                                                             |
| **B** | エージェント実装＋実機検証必要 | エージェントはコードと**実機確認手順書**まで作る。実機確認は人手。成果物は「実機未検証」として提出する。    |
| **C** | 人間・調達ブロック             | SDK入手、ライセンス確認、部品型番の特定、配線変更、植物・水の準備。エージェントは着手せず、調査メモのみ作成する。 |

### 運用ルール

1. **Aを最大化し、Aから先に消化する。** レジスタを直接叩く処理と、判定・計算・符号化のロジックを必ず分離し、後者をAにする。
2. **Bのカードには、実機で何を測り、何が出れば合格かを数値で書く。** 「動作を確認する」では不足。
3. **Cには着手しない。** 型番や仕様を推測してドライバを書くことは禁止。
4. **実機で確認していないことを「動作確認済み」と書かない。** PR本文に必ず`実機未検証`と明記する。

## 4. 不変制約

違反した変更はレビューで差し戻します。

### 4.1 メモリ資源

`firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/ML63Q25x7_lccarm.ld`より。

| 項目                         |                                            値 |
| ---------------------------- | --------------------------------------------: |
| Flash（`__FLASH_SIZE`）    |        0x0003FFC0 = 262,080 byte（約256 KiB） |
| コードオプション領域         | 0x1003FFC0 から64 byte（Flash末尾、変更禁止） |
| RAM（`__RAM_SIZE`）        |            0x00004000 = 16,384 byte（16 KiB） |
| スタック（`__STACK_SIZE`） |                            0x400 = 1,024 byte |
| ヒープ（`__HEAP_SIZE`）    |                            0xC00 = 3,072 byte |

→ `.data + .bss`に使えるのは**約12 KiB**。実測はP0-3で行います。

- 動的メモリ確保（`malloc`/`free`/可変長配列）は使用しない。
- 16 KiBのRAMに長期の時系列は置けません。記録は基板搭載FeRAM（§5）へ保存します。

### 4.2 時間予算

`board/BoardTimer.c`のTimer0割り込みがLSCLK 32,768 Hzで10 msごとに`s_pendingTicks`を加算し、
`App_RunOnce()`が`while (Board_Take10MsTick())`でまとめて消化します。

- **1 tick（10 ms）以内に終わらない処理は、tickを分割して複数回に分ける。**
- 長いループの中では`wdt_clear()`を呼ぶ（ウォッチドッグは`WDT_2S`）。
- 時間の計算はtick数で行う。壁時計時間を仮定しない（tickはまとめて消化されるため）。
- **`s_pendingTicks`は`uint8_t`で255で飽和するため、`PLANT_DOCTOR_ERROR_TICK_OVERFLOW`は
  約2.55秒ぶんのtickが溜まるまで立ちません。** ウォッチドッグ（2秒）のほうが先に効くため、
  現状のファームウェアは**1 tick〜2.5秒のメインループ遅延を検出できません**。
  P0-4で最大未処理tick数のウォーターマークを追加し、遅延を可観測にします。
- 割り込みハンドラは10 ms tickの記録だけ。I2C、SPI、ADC、LCD、UARTの同期転送はすべてmainコンテキスト。
- **R4の「センサ取得、ストレス推定、表示、ポンプ制御を同時に実行する」は、
  この10 ms tickのスーパーループ上での並行動作として実現します。** RTOSは導入しません。

### 4.3 変更してはいけないファイル

`CODING_RULES.md`の「生成コードとの境界」より。

```text
firmware/ml63q2557/CommonFiles/                      ベンダー提供ドライバ
firmware/ml63q2557/external/CMSIS/                   submodule
.../PlantDoctor/startup_ML63Q25x7.c
.../PlantDoctor/system_ML63Q25x7.*
.../PlantDoctor/ML63Q25x7.*
.../PlantDoctor/NmiHandler.c
.../PlantDoctor/codeoption*
.../PlantDoctor/*.ld
.../PlantDoctor/drivers/                             ドライバサンプル由来
.../PlantDoctor/.project / .cproject / .settings/    LEXIDE-Ω資産
```

ベンダードライバの挙動を変えたい場合は、**ユーザーコード側にラッパーを追加する**。
`CommonFiles/`を編集しない。

### 4.4 その他

- Windows／macOS両対応を維持する。いずれかのOSの絶対パスを共通設定へ直書きしない。
- `CODING_RULES.md`に完全準拠する（ファイルヘッダの`=`デコレーション、`@brief`は名詞・動詞形、
  行末コメントは61桁目、連続`#define`の値は44桁目、K&R中括弧、`static const`はファイルスコープ、
  関数内部はDoxygen形式を使わない、など）。カード完了前に同文書末尾のチェックリストを通す。
- 浮動小数点演算を使わない（Cortex-M0+にFPUなし）。固定小数点・整数演算で実装する。
- ROHM／DATA TECNO由来のSDK・プリビルドライブラリ・DFPは**コミットしない**。
  `firmware/ml63q2557/.tooling/`または`external/`に置き、`.gitignore`対象のままにする。
- 型は`stdint.h`の固定幅型と`stdbool.h`の`bool`。ベンダーAPI境界の型はそのまま維持する。
- **R7（装置単体で完結）**：外部通信に依存する実装を入れない。
  UART（§5）はログ取り出しと設定のための開発・デモ用途であり、診断機能はUARTなしで完結させる。

### 5.1 R2（学習）に必要な時系列の容量

R2の「時間単位で葉温がどの程度上がるか、土壌水分がどの速度で下がるか」を学習するには、
昼夜を含む長期の時系列が必要です。24 byte固定長レコード（P2-2）・60秒周期で計算すると：

| 期間   | レコード数 |         容量 |
| ------ | ---------: | -----------: |
| 24時間 |      1,440 |  34,560 byte |
| 7日    |     10,080 | 241,920 byte |

FeRAMのレコード領域（§P2-3で261,632 byte）に**約7.5日分**入ります。RAMでは成立しません。

### 5.2 表示デバイス — 企画の4行表示と実ハードの差

企画の表示例は**4行・最大22桁**です。

```text
Plant Stress: 24 / 100        22桁
Status: Healthy               15桁
Leaf-Air Temp: +0.8C          20桁
Soil Trend: Stable            18桁
```

実ハードは**16文字×2行のキャラクタI2C LCD**です
（`drivers/Lcd.h`の`LCD_MOST_CHARACTERS_ON_A_LINE = 16`、`LCD_START_OF_FIRST_LINE = 1`、
`LCD_START_OF_SECOND_LINE = 17`、`LCD_END_OF_SECOND_LINE = 32`）。
ハードウェアユーザーズマニュアルにOLEDの記載はなく、基板にOLEDは載っていません。

**企画の4行はそのままでは1行も収まりません。** R6の4項目は、既存の5秒ページ切替・1秒更新の
仕組みを使った**ページ表示**として実現します。割り当て案はP4-4に置きます。
OLEDを追加する選択肢もありますが、**既定は16×2 LCDのページ表示**とします（§6 G12）。

### 5.3 まだ確定していないこと（推測で実装しないこと）

1. **FeRAMとRTCのIC型番、コマンドセット、レジスタマップ。**
   ハードウェアユーザーズマニュアルは §5.13「SPI」、§5.14「FeRAM」、§5.15「RTC」に記載がありますが、
   本計画作成時のテキスト抽出では日本語本文が欠落しました。**PDF原文と回路図で型番を特定してから**
   ドライバを書くこと（P2-1）。FeRAMの`READ`/`WRITE`/`WREN`オペコードとアドレス長（2 byte / 3 byte）、
   RTCのレジスタ配置とBCD/バイナリ表現は品種で異なります。
2. **FeRAMの`/WP`（ライトプロテクト）の扱い。**
   確実に言えるのは次の2点だけです。

   - ハードウェアマニュアルのテストポイント一覧に`WP_B` / `FeRAM /WP Signal`という信号が存在する。
   - `SoftSpi.c`の`P8MOD0_PARAM = 0x05020201`のコメントは`P83:In PullUp P82:Out P81:Out P80:In`であり、
     **`SoftSpiPeripheralInit()`はP80を入力に設定して、それ以降P80を一切操作しません。**

   一方、**`/WP`がP80に接続されているのか、外部プルの向きがどちらなのかは確認できていません。**
   PDFのピン一覧はテキスト抽出で2列が混ざり、同じ`/WP`信号が異なるテストポイント番号で2回現れ、
   方向表記も`SoftSpi.c`の`P80:In`と矛盾します。**回路図で確認するまで、P80が`/WP`だと仮定しないこと。**
   `/WP`がLowのときにメモリ配列への書き込みまで禁止される品種であれば、書き込みは失敗します。
3. **Soft SPIの転送時間。**
   `oneClock()`は`volatile int`のインクリメントでパルス幅を稼ぐビットバンギングです。
   1 bitあたり数十サイクル程度と見込まれ、24 byteのレコード書き込みは数百µsのオーダーと予想されますが、
   Debug（`-O0`）とRelease（`-Os`）で差が出ます。P0-4のtick遅延計測で実測してください。
4. **Solist-AIの学習・推論ライブラリと`ML_ACC_CTRL*`の仕様。**
   リポジトリに存在せず、`VSCODE_SETUP.md`に「Solist-AIのプリビルドライブラリは……この移行では
   コピーしていません。利用を開始するときは、参照テンプレートのライセンスとROHMファイルの
   再配布条件を確認してから追加します」と明記されています。**R2の本体（P7）が着手できません。**

### 7.2 実行順序

```text
P0 開発基盤 (A)
 ├── P1 センサ取得と変化量 (A)
 │     ├── P3 妥当性・整合性判定 (A)
 │     │     └── P4 診断と表示 (A/B)
 │     │           ├── P5 給水制御 (A/B)
 │     │           │     └── P6 水やり後の自己診断 (A/B)

 │     └── P2 時刻・記録・校正 (A/B)   ← P4/P6の「平常値」の根拠を作る
 └── （P2-7の実測データが P4/P6 の暫定基準を決める）
```

### 7.3 優先順位

1. **P0-1 / P0-2**（ホストテストとCI）— これが無いと以降の成果を誰も検証できません。最優先。
2. **P0-3 / P0-4**（メモリとtick遅延の可観測化）— R2／R4の実現可能性を実測で判断する土台。
3. **P1**（変化量の算出）— R1。P3／P4／P6のすべての入力になる。
4. **P2-1**（FeRAM／RTCの型番特定）— C分類。人間作業だがP2-2以降のブロッカーなので早く出す。
5. **P3 / P4**（判定と表示）— **ここまででDEMO1・DEMO2・DEMO5が成立します。**
6. **P5-1 / P5-2**（実機安全確認）— **実水を通す前に必ず。**
7. **P5-5**（自律水やり）→ **DEMO3が成立。**
8. **P6** → **DEMO4が成立。**
9. **P8**（デモモード）— 全デモを短時間で再現できるようにする。
10. **P7**（学習）— SDK入手後に再計画。


### 7.4 実機到達マイルストーン M2〜M6

M2〜M6は、P0〜P8のタスクカードを横断して「何が実機で成立したら次の段階へ進めるか」を示す受入ゲートです。
**マイルストーン番号を実装順序として使わず、実装順序は§7.2〜§7.3に従います。**

| マイルストーン | 到達点 | 主に対応するPトラック |
| --- | --- | --- |
| **M2** | 校正、時刻、ログ、特徴量 | P0、P1、P2、P3 |
| **M3** | 手動給水と安全制御 | P5-1、P5-2、P5-3 |
| **M4** | 給水後の応答評価 | P5-4、P6 |
| **M5** | ストレス表示とオンデバイス学習 | P4、P7 |
| **M6** | 展示・デモ・連続運転 | P4-4、P8 |

#### M2: 校正、時刻、ログ、特徴量

AIに渡すデータの意味を固定する段階。

- SEN0193について乾燥時・十分に湿った時の値を記録し、鉢ごとの校正値を設定として保存する。
- RTCを有効化し、測定値・状態・給水イベントを時刻付き固定長レコードにする。
- FeRAMの接続・仕様を確認後、リングバッファとしてログを保存する。
- 土壌水分の移動平均と変化速度、葉温－気温、葉温変化速度、照度、湿度、前回給水からの時間を計算する。
- 再起動、欠測、センサ異常をログから区別できるようにする。

**完了条件**：昼夜を含む24時間以上の時系列と給水イベントを取得でき、再起動・欠測・センサ異常が記録から判別できる。
P2-7ではさらに72時間データを取得し、暫定の平常値を決める。

#### M3: 手動給水と安全制御

自動判定の前に、ポンプを安全に、かつ結果を測りながら動かせるようにする。

- OUT0を明示的にOFFへ初期化し、起動直後、リセット、ウォッチドッグ復帰、システムエラー時は必ずポンプOFFとする。
- 手動給水はLCD/スイッチ（SW4）から短時間（2.0秒）だけ要求できるようにする。
- 一回の最大ON時間（2.0秒）、クールダウン（3.0秒）を維持する。
- 液面なし時の給水拒否インターロックを実水配管前に有効化する。
- センサ診断異常時はシステム全体を停止させず、自律給水の判断側で給水を許可しない。
- 外部電源とポンプを接続する前に、SSR出力とDFR0457信号をテスターで確認する。

**完了条件**：ポンプ未接続でSSR動作を確認後、水系を監視した状態で短時間給水を行える。異常時や連打時にポンプがONにならない。
詳細な数値基準はP5-1／P5-2を正とする。

#### M4: 給水後の応答評価

企画の「水をやった結果まで診る」を、AI導入前の説明可能なルールで実現する。

- 給水前の土壌水分、給水時間、停止理由を給水イベントとして残す。
- 給水直後・遅延後の土壌水分増加量と葉温の落ち着きを再評価する。
- 増加量不足などを`WATERING_RESPONSE_FAILED`として扱い、連続再給水せず警告へ遷移する。
- 液面情報は、水切れ候補の優先度を上げる補助情報にする。
- 普段と異なる土壌水分応答が継続する場合は土壌劣化候補として扱う。

**完了条件**：通常給水と、タンク空・ホース外れ相当の「土壌水分が回復しない」条件を、表示とログで区別できる。

#### M5: ストレス表示とオンデバイス学習

Solist-AI導入前にルールベース版を成立させ、SDK入手後に学習版へ差し替えられる境界を維持する。

- 0〜100の値は「平常状態からのずれ」と定義し、病名や健康度を断定しない。
- 学習未完了、通信異常、疑似入力、すでに異常と判断した期間のデータは正常学習に混ぜない。
- 先行学習テーマは「給水後の土壌水分応答の異常検知」とし、次に日周を含む複数特徴量から植物ごとの平常状態を学習する。
- AIの異常度のみで給水せず、土壌水分・センサ健全性・液面・安全上限と組み合わせて判断する。
- Solist-AI SDK、GCC、必要RAM、モデル保存方式は最小プログラムで実測してから本体へ統合する。

**完了条件**：未学習時は`LEARNING`を表示し、学習済みデータと別期間の記録で、P4の固定しきい値方式との比較ができる。
P7の前提が未解消の間は、P4のルールベース版を完成させてもM5全体は完了扱いにしない。

#### M6: 展示・連続運転

- LCDのページ表示を、`Stress`、状態、葉温－気温、土壌傾向、センサ異常、給水結果へ整理する。
- 熱変化、乾燥・給水、給水失敗、センサ異常を短時間で再現するデモモードを追加する。
- 通常モードとデモモードを明確に区別し、デモモードでも給水安全上限を無効化しない。
- 全デモ後もログ、表示、10 msスーパーループが破綻していないことを確認する。

**完了条件**：通常診断、熱ストレス傾向、乾燥給水、給水失敗、センサ異常の各デモを再現でき、通常モードで72時間以上の連続運転を行ってもログと表示が破綻しない。
詳細な合格基準はP8-2／P8-3を正とする。

### 7.5 直近の作業

1. **P0-1 / P0-2**：ホスト単体テスト基盤とCIを先に作る。
2. **P2-1を人間作業として並行開始**：FeRAM／RTCのIC型番、`/WP`、SPI条件を確定する。
3. **P0-3 / P0-4**：RAMと10 msループ遅延を可視化する。
4. **P1**：土壌校正と特徴量を実装する。
5. P2-1の結果が揃い次第、**P2-2〜P2-6**へ進み、M2のログ基盤を完成させる。

したがって、「鉢ごとの土壌水分校正値を定義し、RTCとログ形式を決める」という旧M2の目的は維持するが、
**その前に自動検証基盤P0を置く**のが統合版の正式な順序である。

  - `Board_`層にも委譲APIを用意し、P2-4のUARTコンソールから読めるようにする。
  - 割り込みと`main`の両方が触る変数なので`volatile`とし、読み出しは既存の
    `__get_PRIMASK()` / `__disable_irq()` / `__enable_irq()`のパターンでクリティカルセクションに入れる。
  - **既存の`s_tickOverflow`の意味は変えない。** 追加のみ。
- **受入条件（A）**：ビルドが通り、クリティカルセクションの入れ方が既存3関数と同一パターンであること。
- **検証手順（B・人手）**：
  1. Debugビルドを書き込み、`MONITOR`状態で5分放置する。
  2. UARTコンソール（P2-4）またはデバッガで`BoardTimer_GetMaxPendingTicks()`を読む。
  3. **合格基準**：センサ取得を含む定常動作で最大未処理tick数が**2以下**。
     3以上ならセンサ取得かLCD転送が10 msを超えているので、原因を記録してカードを起票する。
  4. P4／P5／P6の実装が入ったあとに再測定し、**R4の同時実行が成立していることを数値で示す。**
- **非スコープ**：遅延が出たときの最適化そのもの。

### P1 センサ取得と変化量の算出（R1）

#### P1-1 サンプルの時刻・連番付与

- **分類**：A／**要求**：R1
- **目的**：現在の`PLANT_SENSOR_SNAPSHOT`には時刻も連番もないため、
  10 ms周期で呼ばれる診断側が「新しいサンプルか、前回と同じ値か」を判別できません。
  変化量（R1）を正しく計算するにはサンプルの同一性判定が必須です。
- **触るファイル**：`sensors/SensorManager.c` / `.h`
- **設計**：
  - `PLANT_SENSOR_SNAPSHOT`に追加する。

    ```c
    uint32_t timestampSeconds;                                  /* 取得時のUNIX秒。未同期時は0xFFFFFFFF */
    uint16_t sampleSequence;                                    /* サンプル取得ごとに増加。新規判定に使う */
    ```

    これは**1秒周期のサンプル数**を数えるカウンタで、`uint16_t`では約18.2時間で折り返します。
    用途は「前回見たサンプルと違うか」の判定だけなので、折り返しは`!=`比較で問題になりません。
  - 追加API：

    ```c
    bool SensorManager_TakeNewSample(PLANT_SENSOR_SNAPSHOT *snapshot); /* 新規サンプルのみ取得 */
    uint16_t SensorManager_GetSampleSequence(void);              /* 最新サンプルのsampleSequence */
    ```
  - **既存の`SensorManager_GetLatest()`の意味は変えない。** 表示経路は影響を受けない。
  - 時刻は`TimeKeeper_GetUnixSeconds()`（P2-5）から取る。P2-5未完了のあいだは`0xFFFFFFFF`を入れる。
- **受入条件**：
  - ARMビルドDebug／Releaseが通る。
  - 既存の表示動作（1秒更新・5秒ページ切替）に変更がないこと。
  - `sampleSequence`のラップアラウンド（65535 → 0）を跨いでも「新規」と判定できること
    （比較を`!=`で行い、**大小比較にしない**）。純関数に切り出せる範囲はホストテストする。
- **非スコープ**：サンプリング周期の変更、センサ追加。

#### P1-2 土壌水分の鉢ごと校正

- **分類**：A（変換ロジック）／ B（実機での校正値取得）／**要求**：R1・R2
- **目的**：SEN0193の生値（0〜4095）を鉢ごとに校正する。
  R2の「植物、鉢、土、設置環境ごとの違いを反映する」の土台であり、
  校正なしでは「乾燥」を判定できません。
- **触るファイル**：`sensors/SoilCalibration.c` / `.h`（新規・純ロジック）、
  `config/PlantDoctorConfig.h`、`storage/PlantLog.*`（設定ブロックへの保存）、
  `console/Console.c`（`C?`／`C=`コマンド）
- **設計**：
  - 校正値は**乾燥時の生値（dry）と十分に湿った時の生値（wet）**の2点。
    `sensors/SoilMoistureSensor.c`は既にCN6の反転増幅回路に合わせて`4095 - adcRaw`を返すため、
    **wet > dry**になる想定。実測で逆なら実装ではなく校正値の取り方を見直す。
  - 変換：

    ```c
    int16_t SoilCalibration_ToPermille(uint16_t raw, uint16_t dry, uint16_t wet);
                                                                /* 生値を0〜1000の相対湿り度へ変換 */
    bool SoilCalibration_IsValid(uint16_t dry, uint16_t wet);    /* 校正値の妥当性判定 */
    ```

    0〜1000の千分率とし、範囲外はクランプする。**「水分率(%)ではない」ことをコメントに明記する。**
  - `SoilCalibration_IsValid()`は`wet > dry`かつ差が最低値（既定200）以上を要求する。
    無効なら既定値へフォールバックし、その旨を`C?`の応答に含める。
- **受入条件（A）**：
  - ホストテストが通る：dry未満、wet超、`dry == wet`、`wet < dry`、境界値、クランプ、無効校正値の判定。
- **検証手順（B・人手）**：
  1. センサを乾いた状態（空中）で`S`を10回読み、生値の平均をdry候補とする。
  2. 十分に湿らせた土（または水）に規定深さまで挿し、安定後に`S`を10回読み、平均をwet候補とする。
  3. `C=<dry>,<wet>`で設定し、`C?`で読み戻す。電源再投入後も保持されることを確認する（P2-3）。
  4. **合格基準**：wet − dry ≥ 200。下回る場合は配線とJP設定（`JP4`／`JP6`／`JP7`）と
     `PIN_CONNECTIONS.md` §4を再確認する。
- **非スコープ**：温度補償、土質ごとの係数、複数鉢対応。

#### P1-3 特徴量（変化量）の算出

- **分類**：A／**要求**：R1
- **目的**：R1が明示する変化量をすべて算出する。
  P3（妥当性判定）、P4（診断）、P6（自己診断）、P7（学習）のすべての入力になります。
- **触るファイル**：`ai/PlantFeature.c` / `.h`（既存を拡張）、`ai/PlantAi.c`、`config/PlantDoctorConfig.h`
- **設計**：
  - 企画が挙げる変化量と、原因候補推定（P4-2）に必要な量を揃える。

    ```c
    typedef struct {
        int32_t soilMoisturePermille;                           /* 校正後の相対湿り度 0〜1000 */
        int32_t soilMoistureMovingAverage;                      /* 直近N分の移動平均 */
        int32_t soilMoistureRatePerHour;                        /* 土壌水分の低下速度（1時間あたり） */
        int32_t leafAirTemperatureDelta;                         /* 葉温－気温 [摂氏1/100] */
        int32_t leafTemperatureRatePerHour;                      /* 葉温の上昇速度（1時間あたり） */
        int32_t illuminanceRaw;                                  /* SEN0228生値 */
        int32_t illuminanceAccumulated;                           /* 積算照度（日照不足の判定用） */
        int32_t relativeHumidityCentiPercent;                     /* 相対湿度の1/100 */
        uint32_t elapsedSinceWateringSeconds;                     /* 前回給水からの経過秒 */
        uint8_t validMask;                                        /* 各特徴量の有効ビット */
    } PLANT_FEATURE_VECTOR;
    ```

    `illuminanceAccumulated`は**R3の「日照不足」判定に必須**です。単発の照度値では出せません。
  - **純関数として実装する**（P0-1の設計ルール）。センサAPIを直接呼ばない。

    ```c
    void PlantFeature_Reset(PLANT_FEATURE_STATE *state);        /* 特徴量状態初期化 */
    void PlantFeature_Update(PLANT_FEATURE_STATE *state, const PLANT_FEATURE_INPUT *input);
                                                                /* 1サンプル分の特徴量更新 */
    void PlantFeature_GetVector(const PLANT_FEATURE_STATE *state, PLANT_FEATURE_VECTOR *vector);
                                                                /* 特徴量ベクトル取得 */
    ```

    `PLANT_FEATURE_INPUT`は`PLANT_SENSOR_SNAPSHOT`から必要な値だけを写した構造体にし、
    `ai/PlantAi.c`が変換して渡す。これで`PlantFeature`はセンサ層に依存しません。
  - **移動平均は固定長リングバッファ**。既定`PLANT_DOCTOR_FEATURE_AVERAGE_SAMPLES = 60`
    （1秒サンプル×60 = 1分）。`int16_t`×60 = 120 byte。
    長い窓が必要なら、1分ごとに間引いた第2段の平均を持つ二段構成にしてRAMを線形に増やさない。
  - **積算照度は1分ごとに間引いた値で積算する**（RAM節約）。窓は既定12時間。
  - **整数演算のみ。** 1時間あたりの変化は`(現在値 - N分前の値) * 60 / N`で求め、`int32_t`で受ける。
  - **無効値は伝播させる。** `validFlags`が落ちているサンプルは移動平均に混ぜず、`validMask`を落とす。
    **「値がないこと」を0で埋めない。**
  - `PlantAi_Process10Ms()`は`SensorManager_TakeNewSample()`（P1-1）で新規サンプルだけを処理する。
- **受入条件**：
  - ホストテストが通る：定常値、単調増加、給水を模した階段入力、無効サンプルの混入、
    起動直後（窓が埋まっていない）、`int32_t`境界、負の葉温－気温差、
    `elapsedSinceWateringSeconds`のリセット、積算照度の窓の押し出し。
  - `PlantFeature.c`が`sensors/`と`board/`のヘッダを一切includeしていないこと。
  - `.bss`増分をPR本文に記載する。
- **非スコープ**：異常・ストレスの判定（P3／P4）、しきい値の決定。

#### P2-2 記録レコード形式とエンコーダ／デコーダ

- **分類**：A／**要求**：R2・R5
- **目的**：学習と解析に渡すデータの意味を固定する。
- **触るファイル**（新規）：`storage/PlantLogRecord.c` / `.h`（純ロジック）
- **設計（G3の既定値。24 byte固定長・リトルエンディアン）**：

  | offset | size | 型           | フィールド                       | 意味                                                                         |
  | -----: | ---: | ------------ | -------------------------------- | ---------------------------------------------------------------------------- |
  |      0 |    4 | `uint32_t` | `timestampSeconds`             | RTC由来のUNIX秒。未同期時は`0xFFFFFFFF`                                    |
  |      4 |    2 | `uint16_t` | `recordSequence`               | **記録したレコード1件ごと**に増加（起動時に0）                         |
  |      6 |    1 | `uint8_t`  | `recordType`                   | 0=定期, 1=給水イベント, 2=起動, 3=エラー, 4=診断結果変化                     |
  |      7 |    1 | `uint8_t`  | `validFlags`                   | bit0 soil / 1 leaf / 2 air+hum / 3 press / 4 lux / 5 tank                    |
  |      8 |    2 | `uint16_t` | `soilMoistureRaw`              | 0〜4095                                                                      |
  |     10 |    2 | `int16_t`  | `leafTemperatureCentiC`        | 摂氏1/100                                                                    |
  |     12 |    2 | `int16_t`  | `airTemperatureCentiC`         | 摂氏1/100                                                                    |
  |     14 |    2 | `uint16_t` | `relativeHumidityCentiPercent` | %RHの1/100                                                                   |
  |     16 |    2 | `uint16_t` | `illuminanceRaw`               | SEN0228生値。lux換算はPC側                                                   |
  |     18 |    1 | `uint8_t`  | `plantStatus`                  | `PLANT_STATUS`（P4-2）                                                     |
  |     19 |    1 | `uint8_t`  | `stressScore`                  | 0〜100、不明時は`0xFF`（P4-3）                                             |
  |     20 |    2 | `uint16_t` | `eventPayload`                 | `recordType`で意味が変わる（給水時間[10 ms]、手動/自動フラグ、増加量など） |
  |     22 |    1 | `uint8_t`  | `bootCount`                    | **再起動の判別に使う**（FeRAM設定ブロックで永続化）                    |
  |     23 |    1 | `uint8_t`  | `crc8`                         | offset 0〜22のCRC-8（多項式0x07、初期値0x00）                                |


  - **再起動・欠測・センサ異常の判別**：再起動 = `bootCount`と`recordSequence`のリセット、
    欠測 = `recordSequence`の飛びまたは`timestampSeconds`の間隔異常、
    センサ異常 = `validFlags`のビット落ちと`plantStatus`。
  - **`recordSequence`は「センササンプル」ではなく「記録したレコード」で数える。**
    サンプルは1秒周期なので`uint16_t`では約18.2時間で折り返しますが、レコードは60秒周期（G2）なので
    折り返しは約45.5日後です。P1-1の`sampleSequence`とは別物として扱ってください。
  - **差分は`uint16_t`のモジュロ演算で求める**こと（`(uint16_t)(current - previous)`）。
    符号付きの単純減算をすると折り返し時に約65,000件の欠測として誤検出されます。
    **PC側のCSVデコーダにも同じ規則を適用する**こと。
  - API（純関数）：

    ```c
    void PlantLogRecord_Clear(PLANT_LOG_RECORD *record);                /* レコード初期化 */
    void PlantLogRecord_Encode(const PLANT_LOG_RECORD *record, uint8_t *buffer); /* 24 byteへ符号化 */
    bool PlantLogRecord_Decode(const uint8_t *buffer, PLANT_LOG_RECORD *record); /* CRC検証付き復号 */
    uint8_t PlantLogRecord_Crc8(const uint8_t *data, uint8_t size);     /* CRC-8算出 */
    uint8_t PlantLogRecord_FormatCsv(const PLANT_LOG_RECORD *record, char *text, uint8_t textSize);
                                                                        /* CSV1行整形 */
    ```
  - `PLANT_LOG_RECORD_SIZE`を`24U`として公開し、**構造体の直接`memcpy`に頼らない**
    （パディングとエンディアンをコンパイラに委ねない）。
  - CRCはソフトウェア実装にする。MCUに`CRC`周辺機器はあるが、ホストテスト可能性を優先する。
- **受入条件**：

  - ホストテストが通る：符号化→復号のラウンドトリップ、CRC不一致の検出、負の温度、
    境界値（`0`／`UINT16_MAX`／`0xFFFFFFFF`のタイムスタンプ／`stressScore = 0xFF`）、
    CSV整形のバッファ長不足、`recordSequence`が`65535 → 0`を跨いだときの差分がモジュロ演算で1になること。
  - 符号化結果のバイト列を**期待値のバイト配列とバイト単位で比較する**テストを1件以上含む。
- **非スコープ**：FeRAMへの書き込み（P2-3）。

#### P2-3 FeRAMドライバとリングバッファ

- **分類**：A（符号化部とインデックス計算）／ B（実機での読み書き・永続性確認）／**要求**：R2・R5。
  **P2-1完了が前提。**
- **触るファイル**（新規）：`storage/Fram.c` / `.h`、`storage/PlantLogRing.c` / `.h`（純ロジック）。
  **変更**：`storage/PlantLog.c` / `.h`（既存スタブを実装）、`firmware/ml63q2557/CMakeLists.txt`、
  `board/Board.c`（`SoftSpiPeripheralInit()`の呼び出し）
- **設計**：
  - `SoftSpi.c`は変更しない。`SoftSpiPeripheralInit()` → `SoftSpiDeviceEnable(SOFT_SPI_DEVICE_FRAM)` →
    `SoftSpiWrite()` / `SoftSpiRead()` / `SoftSpiDuplex()` → `SoftSpiDeviceDisable()`の順で使う。
  - `SoftSpiPeripheralInit()`は`Board_Init()`で1回だけ呼ぶ。`PORT8`の`P8MOD0`/`P8MOD1`を
    `write_bit`で上書きするため、`PORT8`を使う他の初期化と衝突しないこと
    （現状`PlantDoctorWorkspace/`配下に`PORT8`を触るコードは無い）。
  - **`/WP`の対処はP2-1の回答が前提**（§5.3-2）。`/WP`がLowに固定されていて、かつメモリ配列の
    書き込みまで禁止される品種だった場合にかぎり、`Fram_Init()`で該当ピンを出力Highへ設定する。
    `P8MOD*`は該当ピンのフィールドのみを`write_bit`で変更する。
    **P80が`/WP`であると仮定して実装しないこと**（§9.3ルール2）。
  - FeRAM API：

    ```c
    bool Fram_Init(void);                                               /* FeRAM初期化と存在確認 */
    bool Fram_Read(uint32_t address, uint8_t *data, uint16_t size);      /* FeRAM読み出し */
    bool Fram_Write(uint32_t address, const uint8_t *data, uint16_t size); /* FeRAM書き込み */
    ```

    `Fram_Init()`は**存在確認**を行う（`RDSR`のビットパターン検証、または予備領域への書き戻し確認）。
    失敗時は`false`を返し、`App_Init()`は既存経路で`PLANT_DOCTOR_ERROR_STORAGE_INTERFACE`へ遷移する。
    書き込みは毎回`WREN`を発行する。1回の呼び出しは**64 byte以内**に制限する（tick予算）。
  - FeRAMマップ（256 KiB、0x000000〜0x03FFFF）：

    ```text
    0x000000 - 0x00007F   設定ブロック（正）        128 byte
    0x000080 - 0x0000FF   設定ブロック（副・二重化） 128 byte
    0x000100 - 0x00017F   リングヘッダ（正）        128 byte
    0x000180 - 0x0001FF   リングヘッダ（副・二重化） 128 byte
    0x000200 - 0x03FFFF   レコード領域 261,632 byte / 24 byte = 10,901レコード
    ```

    60秒周期なら**約7.5日分**。
  - 設定ブロック：magic、format version、土壌水分校正値（dry/wet、P1-2）、記録周期、`bootCount`、
    平常値の暫定基準（G11）、CRC-8。
  - リングヘッダ：magic、`writeIndex`、`recordCount`、`wrapCount`、CRC-8。
  - **二重化の理由**：ヘッダ更新中の電源断で全記録を失わないため。
    正→副の順で書き、両方のCRCを検証して新しい方を採用する。
  - `PlantLog`のAPI：

    ```c
    bool PlantLog_Init(void);                                   /* 記録領域初期化とヘッダ復元 */
    bool PlantLog_AppendRecord(const PLANT_LOG_RECORD *record); /* 1レコード追記 */
    bool PlantLog_ReadRecord(uint16_t index, PLANT_LOG_RECORD *record); /* 古い順にindex番目を読む */
    uint16_t PlantLog_GetRecordCount(void);                     /* 保持レコード数 */
    bool PlantLog_Erase(void);                                  /* 全消去 */
    void PlantLog_Process10Ms(void);                            /* 書き込み状態機械の進行 */
    ```
  - **tick予算**：1レコード（24 byte）の書き込み＋ヘッダ更新は`Process10Ms()`の状態機械で
    **複数tickに分割**する。1 tickでFeRAMへ投げるのは1トランザクションまで。
  - `PlantLogRing.c`にはインデックス計算だけを置き、FeRAMアクセスを含めない（ホストテスト対象）。
- **受入条件（A）**：
  - FeRAMのコマンドフレーム組み立て（オペコード＋アドレス→バイト列）を`SoftSpi`から切り離した
    純関数にし、そのホストテストが通る（アドレス0、末尾アドレス、境界跨ぎ）。
  - `PlantLogRing`のホストテストが通る：空、1件、満杯直前、満杯、ラップ1周、ラップ複数周、
    `PlantLog_ReadRecord(0)`が常に最古を返すこと、ヘッダCRC破損時の副ブロックへのフォールバック。
- **検証手順（B・人手）**：
  1. 書き込み前に`PIN_CONNECTIONS.md`の「電源投入前チェック」を実施する。
  2. UARTコンソール（P2-4）に一時的な`F`コマンド（任意アドレスへ書いて読み戻す）を追加して確認する。
  3. **合格基準**：アドレス`0x000000`／`0x020000`／`0x03FFE0`の3箇所で、
     書いた32 byteが**バイト単位で一致**して読み戻せる。
  4. 電源を切って再投入し、同じ値が読めること（不揮発性）。
  5. `X!`で消去 → 5分放置 → `D`で5件前後のCSVが出ること。
  6. 書き込み中に電源を落とす操作を5回行い、`D`が毎回**パースできるCSVを返す**こと
     （末尾1レコードの欠落は許容、ヘッダ破損による全損は不合格）。
  7. `F`コマンドは検証後に削除するか、デバッグビルド限定にする。
- **非スコープ**：摩耗平準化（FeRAMは10<sup>13</sup>回級なので不要）、圧縮。

#### P2-4 UARTコンソール

- **分類**：A（実装・ホストテスト）／ B（実機でのPC接続確認）／**要求**：G6（R7の制約下での開発手段）
- **目的**：時刻設定、校正値設定、記録のCSV取り出し、内部状態の観測をPCから行う。
  **R7（装置単体で完結）に反しないよう、診断機能はUARTがなくても完結させる。**
  UARTは開発・校正・デモ・データ解析のための経路です。
- **触るファイル**（新規）：`console/Console.c` / `.h`（コマンド解釈・純ロジック）、
  `console/ConsoleUart.c` / `.h`（`uartf1`ラッパー、送受信リングバッファ）。
  **変更**：`firmware/ml63q2557/CMakeLists.txt`、`app/App.c`、`config/PlantDoctorConfig.h`
- **設計**：
  - 物理層：UARTF1 → FT2232H Port B → CN9（USB Type-C）→ PC仮想COMポート。
    ボーレートは**115200 bps**を既定とし、`uartf1_init()`の`brDivisorLatch`をPLL 48 MHzから算出する。
    **算出根拠をコメントに残す。**
  - 行書式：ASCII、`\r\n`終端、1行最大32 byte。応答は先頭`OK `または`ERR `。
  - **`Console.c`はログ・時刻・センサのモジュール関数を直接呼ばない。**
    アクセスは`Console_Init()`に渡す**依存注入の構造体**経由にする。
    これがないとコマンドのホストテストが書けません。
    構造体のメンバ型を書くための`PlantLogRecord.h`・`SensorManager.h`のinclude（型定義のみ）は可。
    `PlantLog.h`・`Rtc.h`・`TimeKeeper.h`はincludeしない。

    ```c
    typedef struct {
        uint16_t (*getRecordCount)(void);                       /* 保持レコード数取得 */
        bool (*readRecord)(uint16_t index, PLANT_LOG_RECORD *record); /* index番目のレコード取得 */
        bool (*eraseLog)(void);                                 /* 記録全消去 */
        uint32_t (*getUnixSeconds)(void);                       /* 現在のUNIX秒取得 */
        bool (*setUnixSeconds)(uint32_t unixSeconds);           /* 時刻設定 */
        bool (*getSnapshot)(PLANT_SENSOR_SNAPSHOT *snapshot);    /* 最新スナップショット取得 */
        bool (*getCalibration)(uint16_t *dry, uint16_t *wet);    /* 校正値取得 */
        bool (*setCalibration)(uint16_t dry, uint16_t wet);      /* 校正値設定 */
        uint8_t (*getMaxPendingTicks)(void);                     /* 最大未処理tick数取得 */
        bool (*setDemoMode)(bool enable);                        /* デモモード切替（P8-1） */
    } CONSOLE_SERVICES;

    void Console_Init(const CONSOLE_SERVICES *services);         /* コンソール初期化 */
    ```
  - コマンド：

    | コマンド             | 応答                                  | 意味                                 |
    | -------------------- | ------------------------------------- | ------------------------------------ |
    | `V`                | `OK <ビルド情報> tick=<n>`          | バージョンと最大未処理tick数（P0-4） |
    | `S`                | `OK <センサ1行>`                    | 最新スナップショット                 |
    | `Q`                | `OK stress=<n> status=<s> soil=<s>` | 現在の診断結果（P4）                 |
    | `T?`               | `OK YYYY-MM-DD hh:mm:ss`            | 現在時刻（P2-5）                     |
    | `T=YYYYMMDDhhmmss` | `OK`                                | 時刻設定                             |
    | `C?`               | `OK dry=<n> wet=<n>`                | 土壌水分校正値（P1-2）               |
    | `C=<dry>,<wet>`    | `OK`                                | 校正値設定                           |
    | `D`                | CSVを複数行出力後`OK`               | 記録全件ダンプ（P2-3）               |
    | `X!`               | `OK`                                | 記録消去。`!`必須の確認付き        |
    | `M=<0\|1>`          | `OK`                                | デモモード切替（P8-1）               |
  - **tick予算を守る**：`Console_Process10Ms()`は1 tickあたり送受信を**固定バイト数まで**に制限する
    （既定16 byte／tick、`PlantDoctorConfig.h`のマクロ）。
    `D`のダンプは「1 tickで1レコード」の状態機械で進め、ループで一気に吐き出さない。
  - 受信バッファ溢れ、不正コマンド、範囲外は`ERR `で返し、状態機械を初期状態へ戻す。
    **UARTの異常でアプリを`ERROR`状態へ落とさない。**
- **受入条件（A）**：
  - ホストテストが通る：全コマンドの正常系、`ERR`になる異常系
    （未知コマンド、桁不足、範囲外の年月日、`X`のみで`!`なし、32 byte超の行）。
  - ARMビルドDebug／Releaseが通り、`.bss`増分をPR本文に記載する。
- **検証手順（B・人手）**：
  1. CN9をPCへUSB Type-Cで接続し、仮想COMポートを115200 bps・8N1で開く。
     必要なら`FT Prog`でPort B = `RS232 UART` / Virtual COM Portに設定する（ハードウェアマニュアル §5.9.3）。
  2. `V`を送り`OK`で始まる1行が返ること。
  3. `S`を10回送り、センサ値がLCD表示と一致すること。
  4. `X!`→`D`で0件、`T=...`→`T?`で設定した時刻が返ること。
  5. **LED1のハートビート（1秒周期）とLCD更新が、UART通信中も止まらないこと**（R4の同時実行）。
- **非スコープ**：バイナリプロトコル、フロー制御、割り込み駆動DMA転送。

#### P2-5 RTCドライバと時刻管理

- **分類**：A（時刻計算ロジック）／ B（実機での時刻保持確認）／**要求**：R2・R5。**P2-1完了が前提。**
- **触るファイル**（新規）：`board/Rtc.c` / `.h`、`app/TimeKeeper.c` / `.h`（純ロジック）、
  `inc/PlantDateTime.h`
- **設計（G4／G5の既定値）**：
  - **基板搭載SPI RTCを正とする。** MCU内蔵RTCは使わない。
    理由：基板のRTCはCR1220でバックアップされ、電源断をまたいで時刻を保持する。
  - `Rtc.c`：`SoftSpiDeviceEnable(SOFT_SPI_DEVICE_RTC)`（CSはHighアクティブ）でレジスタを読み書きする。
    レジスタ配置とBCD／バイナリの別はP2-1のメモに従う。

    ```c
    bool Rtc_Init(void);                                        /* RTC初期化と発振確認 */
    bool Rtc_ReadDateTime(PLANT_DATE_TIME *dateTime);           /* RTC日時読み出し */
    bool Rtc_WriteDateTime(const PLANT_DATE_TIME *dateTime);    /* RTC日時書き込み */
    ```
  - **読み出しのキャリー対策**：秒を跨ぐ瞬間に不整合な値を読む可能性があるため、
    2回読んで一致するまで最大3回再読み出しする。データシートに専用手順があればそれに従う。
  - `TimeKeeper.c`：起動時に`Rtc_ReadDateTime()`でUNIX秒へ変換して保持し、
    以後は10 ms tickを100回数えて1秒ずつ進める。**60秒ごとにRTCと再同期**する。

    ```c
    void TimeKeeper_Init(uint32_t unixSeconds, bool synchronized); /* 秒カウンタ初期化 */
    void TimeKeeper_Tick10Ms(void);                             /* 10ms tick加算 */
    uint32_t TimeKeeper_GetUnixSeconds(void);                   /* 現在のUNIX秒 */
    bool TimeKeeper_IsSynchronized(void);                       /* RTC同期済み判定 */
    void TimeKeeper_Resynchronize(uint32_t unixSeconds);         /* RTC値での再同期 */
    uint32_t TimeKeeper_ToUnixSeconds(const PLANT_DATE_TIME *dateTime); /* 日時→UNIX秒 */
    void TimeKeeper_FromUnixSeconds(uint32_t unixSeconds, PLANT_DATE_TIME *dateTime);
                                                                /* UNIX秒→日時 */
    ```
  - **RTCが読めない／未設定でも動作を止めない。** `TimeKeeper_IsSynchronized()`が`false`のとき、
    レコードの`timestampSeconds`は`0xFFFFFFFF`とし、`recordSequence`で順序を保つ。
    **RTC異常で`ERROR`状態へ落とさない。**
  - `PLANT_DATE_TIME`は`inc/`に置き、年（西暦）・月・日・時・分・秒・曜日を固定幅型で持つ。
- **受入条件（A）**：
  - ホストテストが通る：うるう年（2024/2/29、2100/3/1）、月末、年跨ぎ、UNIX秒との往復変換、
    `0xFFFFFFFF`の扱い、tick 100回で1秒進むこと、再同期時の飛び。
- **検証手順（B・人手）**：
  1. `T=20260911120000`で時刻を設定し、`T?`で読み戻す。
  2. 10分放置し、`T?`の値が壁時計と**±2秒以内**で一致すること。
  3. ボードの電源を切り、5分後に再投入 → `T?`が経過時間を含んだ正しい時刻を返すこと
     （CR1220バックアップの確認）。CR1220が未装着なら装着してから実施する。
  4. `D`のCSVに時刻列が入っていること。
- **非スコープ**：`RTCINT_B`割り込みによる定期起床、タイムゾーン、夏時間。

- **触るファイル**：`storage/PlantLog.c`、`app/App.c`、`ai/PlantAi.c`、`config/PlantDoctorConfig.h`

#### P2-7 長期データの取得と平常値の暫定基準の決定

- **分類**：**B／C**（実機と植物が必要）／**要求**：R2・R3・R5の前提（G11）
- **目的**：R2の学習が使えない段階でも、R3のバロメータとR5の「普段と異なる」を判定するには
  **「普段」の数値が必要**です。実測から暫定基準を決めます。
- **前提**：P1、P2-2〜P2-6完了。
- **検証手順（人手）**：
  1. 校正値を設定し（P1-2）、時刻を合わせ（P2-5）、`X!`で記録を消去する。
  2. テラリウムに植物・土・センサを設置し、**ポンプは外したまま**、昼夜が入るように72時間連続運転する。
  3. 途中で手動給水（SW4）を数回行う。1回はI2Cセンサを1台抜いた状態で行う。
  4. 途中でリセットを1回入れる。
  5. `D`でCSVを取得し、PCで次を確認・算出する。
- **合格基準（データの健全性）**：
  - レコード数が期間から期待される件数の±2%以内。
  - `recordSequence`の飛び（**`uint16_t`のモジュロ差分**）から欠測が特定でき、飛びが**全体の1%未満**。
  - リセット位置が`bootCount`の変化と`recordType=2`で特定できる。
  - センサを抜いた区間が`validFlags`のビット落ちで特定できる。
  - 給水操作が`recordType=1`で時刻と給水時間つきで残っている。
  - 気温・照度に昼夜の周期が見える。
- **成果物（P4／P6の入力になる暫定基準）**：
  - 葉温－気温差の平常範囲と、熱ストレスと呼ぶべき値（DEMO2の`+2.0C`が根拠になる）
  - 土壌水分の1時間あたり低下速度の平常範囲
  - 給水後の土壌水分の増加量と安定化時間の平常範囲
  - 昼夜の積算照度の平常範囲（日照不足のしきい値）
  - これらを`config/PlantDoctorConfig.h`のマクロ初期値として提案し、
    **「P2-7の実測に基づく暫定値」とコメントに明記する。**
- **注意**：この値はP7（学習）で置き換えられる前提の暫定値です。
  **固定しきい値のまま完成としない**（R2）。

### P3 センサ値の妥当性・整合性判定（R3・DEMO5）

#### P3-1 範囲チェックと整合性チェック

- **分類**：A／**要求**：R3（センサ異常）・**DEMO5**
- **目的**：DEMO5「いずれかのセンサが**明らかな異常値**を示す状態」「**土壌水分センサを土から抜く**」
  「他のセンサは正常に変化している状態にする」を検出する。
  現状の`validFlags`は**通信の成否だけ**で、通信成功のまま妥当でない値を返すケースを検出できません
  （`sensors/LeafTemperatureSensor.c:78`のINT16オーバーフローガード以外、範囲チェックはゼロ）。
  **土から抜いたSEN0193はADC読み出しに成功するため、通信ベースでは絶対に検出できません。**
- **触るファイル**（新規）：`sensors/SensorPlausibility.c` / `.h`（純ロジック）。
  **変更**：`sensors/SensorManager.c`、`config/PlantDoctorConfig.h`
- **設計**：
  - **3段の判定**にする。既存の`validFlags`（通信成否）は**変更せず**、別のマスクを追加する。

    | 段        | 判定                 | 例                                                                                                                           |
    | --------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
    | 1. 通信   | 既存の`validFlags` | NACK、タイムアウト、PECエラー                                                                                                |
    | 2. 範囲   | 物理的にありえない値 | 気温 < −40℃ / > 85℃（BME280仕様）、湿度 > 100%、葉温 < −70℃ / > 380℃（MLX90614仕様）、土壌水分が校正範囲を大きく外れる |
    | 3. 整合性 | 他センサと矛盾する値 | 葉温－気温差が ±20℃を超えて継続、照度が完全に0のまま継続（センサを覆った状態）、土壌水分が1サンプルで急変（挿抜）          |
  - 追加する型：

    ```c
    typedef enum {
        SENSOR_HEALTH_OK = 0,                                   /* 正常 */
        SENSOR_HEALTH_NO_COMMUNICATION,                         /* 通信不能 */
        SENSOR_HEALTH_OUT_OF_RANGE,                             /* 範囲外の値 */
        SENSOR_HEALTH_INCONSISTENT                              /* 他センサと矛盾 */
    } SENSOR_HEALTH;
    ```

    **`SENSOR_HEALTH`は「センサIC単位」ではなく「値のグループ単位」で持つ。**
    グループは`soil` / `leaf` / `air+hum` / `lux`の4つで、これは既存の`validFlags`のビット構成と揃います。
    **どのグループが異常かを区別できること**がDEMO5の`Soil Sensor Error`表示の前提です。

    **注意**：`sensors/EnvironmentSensor.c`は**BME280（気温・湿度・気圧）とSEN0228（照度）の
    両方を1モジュール・1回の`EnvironmentSensor_Read()`で扱います**（モジュールは3つで、
    値のグループは4つ）。`ENVIRONMENT_SENSOR_SAMPLE`が`airTemperatureValid`と
    `illuminanceValid`を個別に持っているため値ごとの判定は可能ですが、
    **CN3のI2Cバス自体の異常では`air+hum`と`lux`が同時に落ちます。**
    「4つの独立したセンサモジュールがある」という前提で実装しないこと。
  - **段3は「継続」で判定する。** 1サンプルの外れ値で異常と断定せず、
    既定で連続5サンプル（5秒）続いたときに異常とする。
  - **土壌水分センサの挿抜検出**は校正値（P1-2）との関係で判定する。
    校正済みdry値より大幅に低い／高い値、または1サンプルでの急変を`OUT_OF_RANGE`とする。
  - **異常を検出しても`ERROR`状態へ落とさない。** 表示と記録で示し、他センサの計測を継続する
    （`ARCHITECTURE.md`の既存方針に沿う）。
  - しきい値はすべて`PlantDoctorConfig.h`のマクロにし、**数値の根拠をコメントに書く**
    （データシートの仕様範囲か、P2-7の実測か、暫定値かを明記）。
  - **液面センサの既知の制限を記録する**：`TankLevelSensor_IsLiquidDetected()`はP64のLowアクティブ入力なので、
    **未接続時に「液面あり」と誤判定する可能性**があります。P5-2の手順4で実機確認し、
    区別できない場合は制限として明記する。
- **受入条件**：
  - ホストテストが通る：各グループの範囲内／範囲外／境界値、葉温－気温差の異常が
    4サンプルでは異常にならず5サンプルで異常になること、照度0の継続、土壌水分の急変、
    通信異常時に範囲・整合性判定をスキップすること、**どのグループが異常かを個別に返すこと**、
    **`air+hum`と`lux`が同時に落ちるケース（CN3バス異常）と`lux`だけが落ちるケース
    （SEN0228を覆う＝DEMO5）を区別できること**。
  - 既存の`validFlags`の意味と表示動作が変わっていないこと。
- **非スコープ**：異常時の表示文字列（P4-2／P4-4）、センサの自動復旧。

### P4 診断と表示（R3・R6・DEMO1・DEMO2）

R3の「固定しきい値で判断するのではなく」という要求の本体はP7（学習）ですが、
**P7はSDK未入手で着手できません**（§5.3-4）。そこでG8のとおり、
**まずSDK非依存のルールベースで0〜100と原因候補を出します。** これは捨て仕事ではありません。
R2が「固定しきい値で判断するのではなく」と言うとき、**比較対象となる固定しきい値方式が必要**であり、
P4がそれになります。P7で内部実装を差し替えられる境界として設計します。

**前提**：P0-1、P1、P3。平常値の数値はP2-7から取ります（G11）。

#### 暫定値の扱い（P4-2／P4-3／P6-2に共通）

P2-7は**植物・テラリウム・72時間・人手**を要する C／B 分類のカードです。
一方P4とP6はA分類で先に進められます。**しきい値の確定を待って止まらないため、次の規則を守ります。**

1. `config/PlantDoctorConfig.h`には**プレースホルダ値**を置き、コメントに`TODO(P2-7)`と
   「P2-7の実測で再調整する暫定値」と明記する。
2. **判定関数はマクロを直接読まない。** しきい値は**引数または状態構造体として外から受け取る**。
   `app/`層がマクロを読んで渡す。
3. **ホストテストはマクロではなく、テスト内で定義した定数を渡す。**
   これで**ロジックの正しさを数値の確定と独立に検証できます。**
   P2-7が終わったらマクロ値を差し替えるだけで済み、テストを書き直す必要がありません。
4. この構造はP7（学習）でも同じ入口を使います。学習値を注入すれば、
   判定ロジックを変更せずに固定しきい値方式から学習方式へ切り替えられます。

**マクロを関数内で直接参照した実装は差し戻します。**

#### P4-1 診断状態の型定義

- **分類**：A／**要求**：R3・R6
- **目的**：企画の表示例から値集合を確定し、型として固定する（§1.2）。
- **触るファイル**：`inc/PlantDoctorStatus.h`（既存に追加）
- **設計**：

  ```c
  typedef enum {
      PLANT_STATUS_HEALTHY = 0,                               /* Healthy */
      PLANT_STATUS_DRY_STRESS,                                /* Dry Stress */
      PLANT_STATUS_HEAT_STRESS,                               /* Heat Stress */
      PLANT_STATUS_LOW_LIGHT,                                 /* 日照不足 */
      PLANT_STATUS_ROOT_UPTAKE,                               /* 根の吸水不良 */
      PLANT_STATUS_WATERING,                                  /* Watering */
      PLANT_STATUS_WATERING_FAILED,                           /* Watering Failed */
      PLANT_STATUS_SOIL_DEGRADATION,                          /* 土壌の劣化 */
      PLANT_STATUS_WARNING,                                   /* Warning */
      PLANT_STATUS_SENSOR_ERROR,                              /* Sensor Error */
      PLANT_STATUS_LEARNING                                   /* 学習未完了（P7） */
  } PLANT_STATUS;

  typedef enum {
      SOIL_TREND_UNKNOWN = 0,                                 /* 判定に必要な履歴が不足 */
      SOIL_TREND_STABLE,                                      /* Stable */
      SOIL_TREND_DRY,                                         /* Dry */
      SOIL_TREND_WET,                                          /* Wet */
      SOIL_TREND_DEGRADATION                                   /* Degradation */
  } SOIL_TREND;

  #define PLANT_STRESS_UNKNOWN               (0xFFU)
  ```

  - **`PLANT_DOCTOR_ERROR`（システムエラー）と`PLANT_STATUS`（診断結果）を混同しない。**
    前者は`ERROR`状態へ遷移する異常、後者は`MONITOR`中の診断結果です。
    DEMO5の`Soil Sensor Error`は**後者**（システムは動き続ける）。
  - enumの値は`recordType`と同様に記録へ入るため、**既存の値の番号を後から変えない。**
- **受入条件**：ARMビルドが通る。既存の`PLANT_DOCTOR_ERROR`に変更がないこと。

#### P4-2 原因候補の推定

- **分類**：A／**要求**：R3・DEMO2・DEMO5
- **目的**：企画が挙げる原因候補を推定する。
- **触るファイル**（新規）：`ai/PlantDiagnosis.c` / `.h`（純ロジック）。
  **変更**：`ai/PlantAi.c`、`config/PlantDoctorConfig.h`
- **設計**：
  - 判定ルール（入力はP1-3の特徴量とP3-1のセンサ健全性。しきい値はP2-7の実測に基づく暫定値）：

    | 候補         | ルール                                                                                | 企画の根拠                                                                          |
    | ------------ | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
    | 土壌の乾燥   | 校正後の土壌水分が乾燥しきい値未満                                                    | 「土壌の乾燥」、DEMO3                                                               |
    | 熱ストレス   | 葉温－気温差が大**かつ** 葉温上昇速度が大                                       | 「葉温の上昇速度、気温との差、照度の変化をもとに、熱ストレス傾向を判定する」、DEMO2 |
    | 日照不足     | **積算照度**が一定期間しきい値未満                                              | 「日照不足」                                                                        |
    | 根の吸水不良 | 土壌水分は十分**かつ** 葉温－気温差が大 **かつ** 給水後も葉温が下がらない | 「土は湿っていても、根がうまく水を吸えていないかもしれない」                        |
    | 水やり失敗   | `WATERING_RESPONSE_FAILED`（P6-1）                                                  | 「水やり失敗」、DEMO4                                                               |
    | 土壌の劣化   | 給水後の水分上昇量が平常より小さい、または低下速度が平常より速い状態が継続            | 「普段と異なる土壌水分の変化の場合は、土壌の劣化などを推定する」                    |
    | センサ異常   | P3-1でいずれかのセンサが`OK`以外                                                    | DEMO5                                                                               |
  - **優先順位を明示的に固定する**（同時成立時に何を表示するか）：

    ```text
    SENSOR_ERROR > WATERING_FAILED > WATERING > DRY_STRESS > SOIL_DEGRADATION
      > HEAT_STRESS > ROOT_UPTAKE > LOW_LIGHT > HEALTHY
    ```

    センサ異常を最優先にするのは、**異常値に基づく診断を表示しないため**です。
  - `Soil Trend`の判定：土壌水分の1時間あたり変化速度から`STABLE` / `DRY` / `WET`、
    平常と異なる変化が継続していれば`DEGRADATION`。履歴不足は`UNKNOWN`。
  - **純関数として実装する**：

    ```c
    void PlantDiagnosis_Reset(PLANT_DIAGNOSIS_STATE *state);    /* 診断状態初期化 */
    void PlantDiagnosis_Update(PLANT_DIAGNOSIS_STATE *state, const PLANT_DIAGNOSIS_INPUT *input);
                                                                /* 1サンプル分の診断更新 */
    PLANT_STATUS PlantDiagnosis_GetStatus(const PLANT_DIAGNOSIS_STATE *state); /* 診断結果取得 */
    SOIL_TREND PlantDiagnosis_GetSoilTrend(const PLANT_DIAGNOSIS_STATE *state); /* 土壌傾向取得 */
    ```
  - **断定しない表現にする。** 表示上は候補として扱い、`?`付きの文字列にする（P4-4）。
  - **しきい値は上記「暫定値の扱い」に従う。** マクロを関数内で直接参照せず、
    引数または状態として外から受け取る。これがP7（学習）で学習値を注入する入口になります。
- **受入条件**：
  - ホストテストが通る：各候補が単独で成立するケース、複数同時成立時の優先順位（全ペア）、
    どれも成立しないとき`HEALTHY`、センサ異常時に他の候補を表示しないこと、
    履歴不足時に`SOIL_TREND_UNKNOWN`、`DEGRADATION`の判定が暫定基準で動くこと。
  - `PlantDiagnosis.c`が`sensors/`・`board/`・`actuator/`の実装に依存しないこと。
  - **DEMO2の入力（葉温－気温差`+2.0C`、照度上昇）で`HEAT_STRESS`になること**をテストで固定する。
- **非スコープ**：0〜100の算出（P4-3）、LCD割り付け（P4-4）、学習（P7）。

#### P4-3 ストレスバロメータ 0〜100

- **分類**：A／**要求**：R3・R6・DEMO1〜DEMO5
- **目的**：企画の中心表示である`Plant Stress: nn / 100`を出す。
- **触るファイル**（新規）：`ai/PlantStress.c` / `.h`（純ロジック）。**変更**：`config/PlantDoctorConfig.h`
- **設計**：
  - **定義**：0〜100は「**平常状態からのずれ**」。健康度でも病気の確率でもない。
    この定義をヘッダのコメントに書く。
  - 特徴量ごとに0〜100の部分スコアを出し、**重み付き最大値**で合成する
    （平均ではなく最大寄り。1つの深刻なずれが平均で薄まるのを防ぐ）。
    重みは`PlantDoctorConfig.h`に置き、**暫定値であることを明記する**。
  - **整数演算のみ。** 部分スコアは0〜100の`uint8_t`、合成の中間は`int32_t`。
  - 有効な特徴量が不足しているときは**0を返さず**、`PLANT_STRESS_UNKNOWN`（`0xFF`）を返す。
    「ずれが無い」と「判定できない」を混同しない。
  - **どのセンサ異常で`PLANT_STRESS_UNKNOWN`にするかを明示的に決める。**
    DEMO5の期待表示は`Stress: 80/100` / `Soil Sensor Error` / `+0.5C` / `Dry`であり、
    **センサ異常中でもストレス値は数値で出ています。** 全部を`--`にすると企画のデモが成立しません。

    | 条件                                          | 戻り値                                                                                 |
    | --------------------------------------------- | -------------------------------------------------------------------------------------- |
    | 有効な特徴量が**1つもない**             | `PLANT_STRESS_UNKNOWN`                                                               |
    | 一部のグループが異常（例：`lux`のみ）       | **残った有効な特徴量から算出した数値**。異常グループの部分スコアは合成に含めない |
    | `soil`が異常だが`leaf`／`air+hum`が有効 | **数値**（DEMO5がこのケース）                                                    |

    **`SENSOR_ERROR`が抑止するのは「診断（原因候補）」であって「測定値の表示」ではありません。**
    P4-2は`Status`を`SENSOR_ERROR`に丸めますが、P4-3のスコアとP4-4のページ1（`LEAF-AIR`／`SOIL`）は
    残った有効値で表示を継続します。
  - **異常グループを除いて合成したことを呼び出し側へ伝える。**
    `PlantStress_Evaluate()`の出力に「合成に使った特徴量のマスク」を含め、
    P2-2のレコードへ残せるようにする（後から「この80は何から出たのか」を追えるようにするため）。
  - **P7でAI版へ差し替えられる境界にする。** `PlantStress_Evaluate()`のシグネチャを変えずに
    内部実装を置き換えられる形にする。
  - **企画の表示例との整合をテストで固定する**：

    | 企画の表示例                                                                           | 期待                  |
    | -------------------------------------------------------------------------------------- | --------------------- |
    | `18 / 100` → `Healthy`                                                            | 全特徴量が平常        |
    | `24 / 100` → `Healthy`                                                            | 軽微なずれ            |
    | `72 / 100` → `Heat Stress`（DEMO2）／`Dry Stress`                               | 1特徴量が大きくずれる |
    | `80 / 100` → `Watering` / `Watering Failed` / `Soil Sensor Error`（DEMO3〜5） | 乾燥が深い            |

    **P4-2のStatus判定と矛盾しないこと**をテストで固定する。
- **受入条件**：
  - ホストテストが通る：上表の4ケース、**有効特徴量が1つもないとき**`PLANT_STRESS_UNKNOWN`、
    **一部グループ異常時に残りから数値が出ること**、0と100のクランプ、部分スコアの重み付き合成、
    **DEMO5の入力（`soil`異常＋`leaf`／`air+hum`正常）で`0xFF`にならず数値が返ること**。
  - **しきい値・重みはマクロを直接読まず、引数または状態として受け取る**（P4冒頭「暫定値の扱い」）。
- **非スコープ**：AI版の実装（P7）、学習データの管理。

### P5 給水制御（R4・DEMO3）

**現状**：`PumpControl_Request(true)`の呼び出し元は`app/AppStateMachine.c:232`のSW4手動操作**1箇所だけ**で、
**自律水やりの経路が存在しません。** R4とDEMO3の核心はここです。

#### P5-1 SSR出力とDFR0457信号の実機確認

- **分類**：**B**（ポンプ・12V電源を接続する前に実施）／**要求**：R4の安全前提
- **前提**：`PIN_CONNECTIONS.md` §11「電源投入前チェック」の全項目。
- **手順**：
  1. **12V電源とポンプを接続しない状態**で、ボードへ給電する。
  2. CN5-9（OUT0a）に`CN3-8`から3.3Vが来ていることをテスターで確認する。
  3. `MONITOR`状態でSW4を押し、CN5-10（OUT0c）の電圧が
     OFF時 ≒ 0 V（開放）→ ON時 ≒ 3.3 V（導通）へ変化すること。
  4. 2.0秒後に自動でOFFへ戻ること（`PLANT_DOCTOR_PUMP_MAX_ON_TICKS = 200`）。
  5. ON中にもう一度SW4を押し、即座にOFFになること（`PUMP STOPPED`表示）。
  6. OFF直後にSW4を連打し、3.0秒間はONにならず`PUMP COOLDOWN`が表示されること
     （`PLANT_DOCTOR_PUMP_COOLDOWN_TICKS = 300`）。
  7. DFR0457のSignal端子でも同じ電圧変化を確認する。
- **合格基準**：2〜7がすべて一致。ON時間が2.0秒 ± 0.1秒。
- **不合格時**：`actuator/PumpControl.c`の`PORT6->P6DO`ビット6の論理（Low = SSR導通）と
  `P6MOD1`のP66モード設定（`PUMP_OUTPUT_MODE = 0x0A << 16`、Nchオープンドレイン出力）を再確認する。

#### P5-2 液面インターロックの有効化と異常系のポンプOFF確認

- **分類**：**B**（G10の人間判断ゲート）／**要求**：R4の安全前提
- **目的**：`PLANT_DOCTOR_PUMP_REQUIRE_LIQUID`が現在`false`のため、**液面なしでもポンプが回ります。**
  実水配管の前に`true`へ変更し、空運転を防ぐ。
- **触るファイル**：`config/PlantDoctorConfig.h`
- **手順**：
  1. `PLANT_DOCTOR_PUMP_REQUIRE_LIQUID`を`(true)`へ変更してビルド・書き込みする。
  2. SEN0204をタンクの水に浸けた状態でSW4 → 給水（`WATERING 2.0s`）。
  3. SEN0204を水から出した状態でSW4 → **ポンプがONにならず**`TANK EMPTY!`が表示されること。
  4. SEN0204を**未接続**にした状態でSW4 → 挙動を記録する。
     `TankLevelSensor_IsLiquidDetected()`はP64のLowアクティブ入力なので、
     **未接続時に「液面あり」と誤判定する可能性**があります。そうなる場合は
     「液面未検出」と「センサ未接続」を区別できないことを既知の制限として記録する（P3-1へ反映）。
  5. 給水中（ポンプON中）にリセットボタンを押す → 起動後にポンプがOFFであること
     （`PumpControl_Init()`が出力設定前に`set_bit`でHighにしている）。
  6. 給水中に電源を切って再投入 → 起動後OFF。
  7. 給水中にLCD I/Oエラーを3回連続発生させ`ERROR LCD`へ遷移させる
     → `AppStateMachine_EnterError()`の`PumpControl_EmergencyStop()`でポンプがOFFになること。
  8. 給水中にウォッチドッグをタイムアウトさせる（デバッグビルドで意図的に長いループを入れる）
     → 復帰後OFF。
- **合格基準**：2〜8すべてで期待どおり。5〜8ではCN5-10の電圧がOFF（≒0 V）になる。
- **注意**：7と8は一時的なコード変更を伴う。**変更を本流へマージしない。**

#### P5-3 P6MOD1設定方法の統一（低優先）

- **分類**：A（実装）／ B（リセット値の確認）／**要求**：R4の堅牢化
- **現状の評価**：`sensors/TankLevelSensor.c`は`set_reg32`（OR）で`P6MOD1`を設定し、
  `actuator/PumpControl.c`は`write_bit`（クリア後セット）で設定しています。
  `PHOTO_COUPLER_INPUT_CONFIG`（bit 0, 8 = P64, P65フィールド）と
  `PUMP_MODE_MASK`（bit 16-21 = P66フィールド）は**重複しないため、現在の動作に不具合はありません**。
  **これは堅牢化であってバグ修正ではない。**
- **手順**：
  1. ML63Q2557のユーザーズマニュアルで`P6MOD1`のリセット値を確認する。
  2. リセット値が0でないフィールドがあるなら、`TankLevelSensor_Init()`を
     `write_bit(PORT6->P6MOD1, <P64/P65のフィールドマスク>, PHOTO_COUPLER_INPUT_CONFIG)`へ変更する。
  3. `App_Init()`の呼び出し順（`SensorManager_Init()` → `PlantAi_Init()` → `PumpControl_Init()`）に
     依存しないことをコメントで明記して固定する。
- **受入条件**：変更後もP5-1とP5-2の手順が合格する。
- **非スコープ**：`PORT6`全体の初期化の集約。

#### P5-4 給水イベントの出力

- **分類**：A／**要求**：R5の前提
- **目的**：`PumpControl`は現在、給水したことを外部へ知らせません。
  R5の自己診断に必要な「給水前の土壌水分、給水時間、停止理由」を上位へ渡せるようにする。
- **触るファイル**：`actuator/PumpControl.c` / `.h`
- **設計**：

  ```c
  typedef enum {
      PUMP_STOP_REASON_MANUAL = 0,                              /* 手動停止 */
      PUMP_STOP_REASON_MAX_ON_TIME,                             /* 最大駆動時間による自動停止 */
      PUMP_STOP_REASON_EMERGENCY                                /* 緊急停止 */
  } PUMP_STOP_REASON;

  typedef struct {
      uint32_t startTimeSeconds;                                /* 給水開始時のUNIX秒 */
      uint16_t onDurationTicks;                                 /* 実際のON時間 [10 ms] */
      uint16_t soilMoistureRawBefore;                           /* 給水直前の土壌水分生値 */
      uint8_t stopReason;                                       /* PUMP_STOP_REASON */
      bool tankLiquidAtStart;                                   /* 給水開始時の液面検出状態 */

  bool PumpControl_TakeWateringEvent(PUMP_WATERING_EVENT *event); /* 未取得の給水イベントを取り出す */
  ```

  - `PumpControl_Request(true)`の成功時に開始情報を記録し、停止時にイベントを確定して1件バッファへ置く。
  - **`PumpControl.c`が`SensorManager`と`TimeKeeper`に依存しないようにする。**
    給水前の土壌水分と時刻は呼び出し側が`PumpControl_SetPreWateringContext()`で渡す。
  - **`PUMP_CONTROL_STATUS_ERROR`は現状どの経路でも返りません。**
    このカードで使うか、使わないなら`@note`で「現状未使用」とコメントする。
    **enumの値は削除しない**（記録の互換性のため）。
- **受入条件**：

  - ARMビルドが通る。`PumpControl.h`が`SensorManager.h`／`TimeKeeper.h`をincludeしていないこと。
  - P5-1の手順（手動停止・自動停止・クールダウン）の挙動が変わっていないこと。
- **非スコープ**：給水するかどうかの判定（P5-5）。

#### P5-5 自律水やりの判定

- **分類**：A（判定ロジック）／ B（実機での自律動作確認）／**要求**：**R4**・**DEMO3**
- **目的**：**企画の「見て、考えて、動く」の『動く』に相当する中心機能。**
- **前提**：P1-2（校正）、P1-3（特徴量）、P3-1（妥当性判定）、P4（診断）、
  **P5-1／P5-2の実機合格**。
- **触るファイル**（新規）：`app/WateringPolicy.c` / `.h`（純ロジック）。
  **変更**：`app/AppStateMachine.c`、`config/PlantDoctorConfig.h`
- **設計**：
  - **判定と実行を分ける。** `WateringPolicy`は「今、給水を要求すべきか」を返す純関数にする。
    実際の`PumpControl_Request()`呼び出しと安全インターロックは既存の層に任せる。

    ```c
    typedef enum {
        WATERING_DECISION_HOLD = 0,                             /* 給水しない */
        WATERING_DECISION_REQUEST,                              /* 給水を要求する */
        WATERING_DECISION_BLOCKED                               /* 乾燥だが安全条件で保留 */
    } WATERING_DECISION;

    WATERING_DECISION WateringPolicy_Evaluate(const WATERING_POLICY_STATE *state,
        const WATERING_POLICY_INPUT *input);                     /* 給水要求の判定 */
    ```
  - **給水するための条件（すべて成立が必要）**：

    | # | 条件                                                                       | 既定値                                           | 根拠                                                                                                                                                                   |
    | -: | -------------------------------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | 1 | 診断結果が`DRY_STRESS` **かつ** 校正後の土壌水分が乾燥しきい値未満 | `PLANT_DOCTOR_WATERING_DRY_THRESHOLD_PERMILLE` | R4「乾燥ストレスが高く、水やりが必要と判断した場合」。**`かつ`にするのは、ヒステリシスで古くなった`DRY_STRESS`だけで給水しないため**（§9.3ルール7：安全側） |
    | 2 | 土壌水分センサが`SENSOR_HEALTH_OK`（P3-1）                               | —                                               | 異常値で給水しない                                                                                                                                                     |
    | 3 | 液面が検出されている                                                       | —                                               | 空運転防止（P5-2）                                                                                                                                                     |
    | 4 | 前回給水から最小間隔が経過                                                 | 1800秒（30分）                                   | 過給水・連打の防止                                                                                                                                                     |
    | 5 | 直近の給水応答が`WATERING_RESPONSE_FAILED`**でない**（P6-1）       | —                                               | R5「連続再給水せず警告へ」                                                                                                                                             |
    | 6 | 1日あたりの給水回数が上限未満                                              | 6回                                              | 過給水の防止                                                                                                                                                           |
    | 7 | アプリが`APP_STATE_MONITOR`                                              | —                                               | エラー中・起動中は給水しない                                                                                                                                           |
  - **条件1のしきい値は固定値から始める**（G11）。`PlantDoctorConfig.h`に置き、
    **P2-7の実測に基づく暫定値であること**をコメントに明記する。
    **これがR2「固定しきい値で判断するのではなく」の比較対象になります。**
  - **自律水やりの有効／無効をマクロで切り替える**
    （`PLANT_DOCTOR_WATERING_AUTO_ENABLE`、既定`false`、G9）。
    P5-1／P5-2の実機安全確認が済むまで`false`のままにする。
  - **安全側の性質**：判定が`REQUEST`でも、`PumpControl`の最大ON時間・クールダウン・
    液面インターロックは**そのまま効く**。**ポリシーはこれらを迂回しない。**
  - 自律給水は`PlantLog`に`recordType=1`・`automatic = true`で記録し、手動と区別する。
  - 給水中は`PLANT_STATUS_WATERING`を表示する（DEMO3の`Status: Watering`）。
- **受入条件（A）**：
  - ホストテストが通る：条件1〜7の**それぞれ単独で不成立**のとき`REQUEST`にならないこと（7ケース）、
    すべて成立で`REQUEST`、`FAILED`後は解除まで`REQUEST`にならない、
    1日上限に達したら翌日までブロック、時刻未同期時の最小間隔判定がtickベースで動くこと。
  - `WateringPolicy.c`が`actuator/`・`sensors/`・`board/`の実装に依存しないこと。
  - `PLANT_DOCTOR_WATERING_AUTO_ENABLE`が`false`のとき、
    **既存の手動給水の挙動が一切変わらないこと**。
- **検証手順（B・人手。P5-1／P5-2の合格が前提）**：
  1. `PLANT_DOCTOR_WATERING_AUTO_ENABLE`を`true`にし、**ポンプを外した状態**で乾いた土にセンサを挿す。
  2. CN5-10の電圧でSSRがONになること。LCDに`WATERING`が出ること。
  3. 液面センサを水から出す → 自律給水が起きないこと。
  4. 土壌水分センサを抜く（P3-1で異常と判定される状態）→ 自律給水が起きないこと。
  5. 給水直後に再度乾燥状態にしても、最小間隔（30分）まで給水しないこと。
  6. **ポンプと水を接続してDEMO3を実施する**（P8）。透明チューブを水が流れること。
- **非スコープ**：AIによる乾燥判定（P7）。

### P6 水やり後の自己診断（R5・DEMO4）

#### P6-1 給水応答の評価（土壌水分と葉温）

- **分類**：A／**要求**：**R5**・DEMO4
- **目的**：R5「ポンプ動作後、**土壌水分が回復したか、葉温が落ち着いたか**を再評価する」。
  **土壌水分と葉温の両方**を評価します。
- **触るファイル**（新規）：`ai/WateringResponse.c` / `.h`（純ロジック）。
  **変更**：`config/PlantDoctorConfig.h`
- **設計**：

  ```c
  typedef enum {
      WATERING_RESPONSE_IDLE = 0,                             /* 給水待ち */
      WATERING_RESPONSE_MEASURING,                            /* 給水後の応答測定中 */
      WATERING_RESPONSE_OK,                                   /* 十分な回復を確認 */
      WATERING_RESPONSE_FAILED                                /* 水分が回復しない */
  } WATERING_RESPONSE;
  ```

  - 評価する量：給水前の土壌水分、給水時間、**給水直後**（既定30秒後）の増加量、
    **遅延後**（既定180秒後）の増加量、安定化時間、**葉温－気温差の低下量**（既定300秒後）。
  - 判定（しきい値は`PlantDoctorConfig.h`、平常値はP2-7）：

    | 土壌水分の回復 | 葉温－気温差の低下 | 判定                                                                                                       |
    | -------------- | ------------------ | ---------------------------------------------------------------------------------------------------------- |
    | あり           | あり               | `WATERING_RESPONSE_OK`                                                                                   |
    | あり           | なし               | `WATERING_RESPONSE_OK`（葉温は遅れるため警告にしない。ただし「根の吸水不良」候補の材料としてP4-2へ渡す） |
    | なし           | —                 | `WATERING_RESPONSE_FAILED`（タンク空・チューブ外れの候補）                                               |
  - **葉温だけで`FAILED`にしない。** 葉温は照度・気流で動きやすく誤判定の原因になる。
    土壌水分が回復していれば給水そのものは成功とみなす。
  - **葉温－気温の「差」を見る**のは、室温変動の影響を外すため。気温そのものを基準にしない。
  - **`FAILED`のとき連続再給水しない。** 警告状態へ遷移し、次の給水要求を拒否する（P5-5の条件5）。
    解除は手動（スイッチ操作またはUARTコマンド）とする。
  - 液面情報（`tankLiquidAtStart`と現在値）は**水切れ候補の優先度を上げる補助情報**として扱い、
    単独で判定しない。
  - 測定中に給水が再要求されたら測定を破棄してやり直す。
  - 土壌水分または葉温が無効な区間は評価に混ぜず、その旨を結果に残す。
  - **純関数として実装する**：

    ```c
    void WateringResponse_Reset(WATERING_RESPONSE_STATE *state); /* 応答評価状態初期化 */
    void WateringResponse_NotifyWatering(WATERING_RESPONSE_STATE *state,
        const PUMP_WATERING_EVENT *event);                       /* 給水イベント通知 */
    void WateringResponse_Update(WATERING_RESPONSE_STATE *state, uint32_t nowSeconds,
        const WATERING_RESPONSE_INPUT *input);                   /* 1サンプル分の応答更新 */
    WATERING_RESPONSE WateringResponse_GetResult(const WATERING_RESPONSE_STATE *state);
                                                                /* 評価結果取得 */
    ```
  - 給水イベントと応答結果を`PlantLog`へ`recordType=1`で記録する
    （`eventPayload`に給水時間・増加量・手動/自動フラグ）。
- **受入条件**：

  - ホストテストが通る：
    - 通常給水（水分回復あり＋葉温低下あり）→ `OK`
    - 水分回復あり＋葉温変化なし → `OK`（かつ吸水不良候補フラグが立つ）
    - **タンク空相当（増加なし）→ `FAILED`**（DEMO4）
    - **チューブ外れ相当（増加なし、液面あり）→ `FAILED`**（DEMO4）
    - 測定中の土壌水分が無効が続く → 測定を延長し、上限で`FAILED`にせず`IDLE`へ戻す
    - 測定中に再給水 → やり直し
    - 時刻未同期（`0xFFFFFFFF`）でも経過時間をtickベースで扱えること
    - 境界：増加量がしきい値ちょうど
    - 給水前後で気温が大きく変わった場合
  - `WateringResponse.c`が`sensors/`・`board/`・`actuator/`の実装に依存しないこと
    （`PUMP_WATERING_EVENT`型のみ参照）。
- **非スコープ**：「根の吸水不良」「土壌の劣化」の推定そのもの（P4-2）。

#### P6-2 土壌の劣化推定

- **分類**：A／**要求**：R5（「普段と異なる土壌水分の変化の場合は、土壌の劣化などを推定する」）
- **目的**：`SOIL_TREND_DEGRADATION`と`PLANT_STATUS_SOIL_DEGRADATION`の判定を実装する。
- **触るファイル**：`ai/PlantDiagnosis.c`（P4-2で新設）、`config/PlantDoctorConfig.h`
- **設計**：
  - 「普段と異なる」を判定するには**平常値が必要**です。P2-7の実測から得た暫定基準を使い、
    **暫定であることをコメントと記録に明記する**（G11）。
    しきい値の渡し方はP4の「暫定値の扱い」に従う（マクロを関数内で直接参照しない）。
  - 判定の材料（いずれも平常範囲との比較）：
    - 給水後の土壌水分の**増加量**が平常より小さい（保水力の低下）
    - 給水後の土壌水分の**低下速度**が平常より速い（排水・保水の変化）
    - 給水後の**安定化時間**が平常より長い
  - **単発で判定しない。** 既定で3回連続の給水サイクルで同じ傾向が出たときに`DEGRADATION`とする。
    土壌の劣化はゆっくり進む現象であり、1回の給水で断定するのは誤りです。
  - `WATERING_RESPONSE_FAILED`（給水系統の異常）と`SOIL_DEGRADATION`（土壌の変化）を**区別する**。
    前者は「水が届いていない」、後者は「水は届いているが土の挙動が変わった」。
    優先順位はP4-2のとおり`WATERING_FAILED` > `SOIL_DEGRADATION`。
  - **P7で学習値へ置き換えられる境界にする。**
- **受入条件**：
  - ホストテストが通る：増加量低下が2回では`DEGRADATION`にならず3回で判定されること、
    低下速度の異常、安定化時間の延長、`FAILED`と`DEGRADATION`が同時成立したときの優先順位、
    平常値が未設定（履歴不足）のとき`SOIL_TREND_UNKNOWN`になること。
- **非スコープ**：土質の分類、肥料・pHの推定。

### P8 デモモード（R8・DEMO1〜DEMO5）

#### P8-1 デモモードの基盤

#### P8-2 企画5デモの成立確認

- **分類**：**B**（実機・植物・水・ライトが必要）／**要求**：**R8**・**DEMO1**〜**DEMO5**
- **前提**：P1〜P6、P8-1完了。P5-1／P5-2の実機安全確認が合格していること。
- **検証手順と合格基準**：

  | デモ                             | 操作                                                                                 | 合格基準（LCDページ0・1の表示）                                                                                                                                                                                                                                                                                       |
  | -------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | **DEMO1** 通常診断         | 電源投入 → センサ値取得                                                             | `STRESS: nn/100`が低値（目安30未満）、`HEALTHY`、`LEAF-AIR`が平常範囲、`SOIL: STABLE`                                                                                                                                                                                                                         |

    疑似入力フラグから特定できる**こと。
  - `BoardTimer_GetMaxPendingTicks()`が**2以下**であること（P0-4、R4の同時実行の実証）。
- **成果物**：各デモの実施記録（表示の写真またはUARTログ）を`docs/`配下またはPRコメントに残す。

## 9. エージェント作業ルール

### 9.1 PRの粒度

- **1カード = 1 PR。** カードを分割したいときは、カードを分割してから複数PRにする。
- PRタイトルにカードIDを入れる（例：`P2-2: 記録レコード形式とエンコーダ／デコーダ`）。
- PR本文に必ず含める：

  ```text
  カード: P2-2
  分類: A
  満たす要求: R2, R5
  実施内容:
  検証したこと:
    - cmake --build --preset debug  : OK
    - cmake --build --preset release: OK
    - ctest --test-dir build/host   : OK (n件)
    - arm-none-eabi-size の .data/.bss 増分: +n byte
  実機未検証: （B分類の場合、何が未検証かを明記）
  採用した既定値: （§6のGn を採用した場合）
  未決事項・申し送り:
  ```

### 9.2 提出前チェックリスト

- [ ] `cmake --build --preset debug`が成功する。
- [ ] `cmake --build --preset release`が成功する。
- [ ] `-Wall -Wextra`の新規警告がゼロ（ベンダーソース以外）。
- [ ] `ctest --test-dir build/host`が成功する（A分類でロジックを追加した場合は**テストを追加している**）。
- [ ] `docs/firmware/CODING_RULES.md`末尾の「作成時の確認項目」を全項目通した。
- [ ] §4.3の変更禁止ファイルを触っていない。
- [ ] `malloc`／`free`／可変長配列／浮動小数点演算を追加していない。
- [ ] 新規の`.data`／`.bss`増分を測り、PR本文に書いた。
- [ ] 1 tick（10 ms）を超える処理を追加していない。追加した場合はtick分割している。
- [ ] Windows／macOS両対応を壊していない（絶対パスの直書きなし）。
- [ ] ROHM／DATA TECNO由来のバイナリ・SDK・DFPをコミットしていない。
- [ ] LCDへ出す文字列が16桁以内である。
- [ ] ドキュメント（`ARCHITECTURE.md`、`PIN_CONNECTIONS.md`、本書）と実装が矛盾していない。
  矛盾する場合はドキュメントも同じPRで更新した。

### 9.3 やってはいけないこと

1. **実機で確認していないことを「動作確認済み」と書く。** B分類の成果物は必ず`実機未検証`と明記する。
2. **型番・レジスタ仕様を推測してドライバを書く。** P2-1が未完了ならFeRAM／RTCのコードを書かない。
   `ML_ACC_CTRL*`の意味を推測しない。
3. **ベンダーコードを編集する。** §4.3のファイルは触らない。対処はユーザーコード側のラッパーで行う。
4. **未決事項で止まる。** §6に既定値があるので、それで進めてPRに明記する。
   §6に無い未決事項が出たら、**カードの「未決事項」に追記してPRを出す**。作業を止めない。
5. **スコープを広げる。** カードの「非スコープ」に書かれたことをしない。
6. **リファクタリングと機能追加を同じPRに混ぜる。**
7. **安全側の制約を緩める。** 最大ON時間、クールダウン、液面インターロック、
   起動時・エラー時のポンプOFFを、テストやデモの都合で無効化しない。**デモモードでも無効化しない。**
8. **記録のレコード形式を後から非互換に変える。** 変える場合は`format version`を上げ、
   PC側デコーダの対応も同じPRに入れる。`PLANT_STATUS`などenumの既存の値の番号を変えない。
9. **「値がない」を0で埋める。** `validFlags`／`SENSOR_HEALTH`／`PLANT_STRESS_UNKNOWN`／
   `SOIL_TREND_UNKNOWN`で「判定できない」を表現する。
10. **固定しきい値のまま完成としない。** P4／P6の暫定値は「P2-7の実測に基づく暫定値」と明記し、
    P7で置き換えられる境界を保つ（R2）。

### 9.4 判断に迷ったとき

- **安全側（ポンプが回らない側）を選ぶ。**
- **記録に残す側を選ぶ。**
- **断定しない側を選ぶ。** 原因は「候補」であり、病名や健康度を断定しない。
- **既存の責務分担を守る。** `ARCHITECTURE.md`の層構造（`app/` → `board/`・`sensors/`・`ui/`）を崩さない。
  レジスタ操作は`board/`・`drivers/`・`sensors/`・`actuator/`・`storage/Fram.c`に閉じ込める。
- **止まらずに、明記する。**
