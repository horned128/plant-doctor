# コーディングルール

`firmware/`配下のCファームウェアにおけるユーザーコードへ適用するコーディング規約です。
本プロジェクトでは、ML63Q2557向けのベアメタルファームウェアを対象とします。

対象範囲は、次のユーザーソース配下です。

```text
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/actuator/
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/ai/
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/app/
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/board/
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/config/
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/examples/
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/inc/
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/sensors/
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/src/
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/storage/
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/ui/
```

## 適用対象と除外

この規約は、ユーザーが作成・保守するアプリケーション、ボード抽象化、センサー、
アクチュエータ、UI、診断サンプルなどのプログラムに適用します。

次のファイルはユーザーコードと混在していても適用対象外です。提供元の書式と内容を
維持し、必要な場合はラッパーまたはユーザーソース側で利用します。

- MCUベンダー、ボードベンダー、SDKが提供するソース・ヘッダ
- スタートアップ、割り込みベクタ、SFR定義、リンカスクリプト、コードオプションなどの生成・定型ファイル
- `CommonFiles/`などの外部ライブラリ、ドライバサンプルから取り込んだコード
- ビルドディレクトリ、オブジェクト、実行形式などの生成物

ユーザー作成か提供元由来か判断できないファイルは、由来を確認するまで変更しません。
現在のツリーでは`examples/sensor_diagnostic/`をプロジェクト保守の診断プログラムとして
適用対象に含め、`drivers/`、プロジェクト直下の起動・SFR・リンカ関連ファイルは除外します。

## 基本方針

- コメントは、コードから読み取りにくい目的・契約・安全上の理由を補足する。
- コメントは日本語で簡潔に書く。
- コードの内容をそのまま言い換えるだけのコメントは書かない。
- 仕様や処理を変更した場合は、関連するコメントも同時に更新する。
- 単位、対象プロセッサ、I2Cなどの通信の意味、タイムアウトなど、誤解しやすい情報は明記する。
- SDKまたはIDEが生成するコードには、原則としてユーザーコメントを追加・編集しない。

## 型とリンケージ

### ML63Q2557ユーザーコード

ML63Q2557向けユーザーコードでは、標準Cの固定幅整数型、`bool`、`static`、`extern`を使用する。
MCUヘッダや周辺機器ライブラリが定義する型は、そのAPI境界でそのまま使用する。

- ファイル内だけで使う関数・変数は`static`、他ファイルへ公開する定義は通常の外部リンケージ、他ファイルが所有する宣言は`extern`を付ける。
- `firmware/ml63q2557/`内のモジュール間インターフェースでは、移植性とwire formatを優先して`stdint.h`の固定幅型と`stdbool.h`の`bool`を使用する。
- API境界で`size_t`が宣言されている場合は、そのシグネチャを維持する。内部の件数・添字には、必要な範囲を表現できる固定幅整数型を使用する。
- ベンダー提供・生成コードは型やリンケージの統一対象に含めず、直接編集しない。

```c
static uint32_t command_age_ms;                            /**< 最終指令からの経過時間 */
extern volatile uint32_t g_command_sequence;               /**< 他モジュールが所有する最終sequence */

int command_send(int16_t left_rpm, int16_t right_rpm);     /* 左右回転数指令送信 */
```

## ファイルヘッダ

ファイルヘッダはDoxygen形式とし、`=`で上下をデコレーションします。

```c
/** =================================================================*
 * @file   main.c
 * @brief  ファームウェアアプリケーション初期化
 * @author Plant Doctor team
 * @date   2026-09
 * ================================================================= */
#include "mcu.h"      /* ML63Q2557のレジスタ定義 */
```

ファイルヘッダの終了行の直後に空行を置かず、最初の`#include`または宣言を続けて記載します。

### `@brief`の書き方

`@brief`は、説明口調の文章ではなく、ファイルが提供する機能を一目で識別できる動詞または名詞の形にします。

```c
 * @brief  ファームウェアアプリケーション初期化
 * @brief  アクチュエータ指令送信
 * @brief  エンコーダカウント取得
```

次のような説明口調は避けます。

```c
 * @brief  ファームウェアアプリケーションを初期化します。
 * @brief  アクチュエータ指令を送信する関数です。
```

## 関数

関数の実装には、ファイルヘッダと同じ形式のDoxygenコメントを付けます。

```c
/** =================================================================*
 * @brief  ファームウェアアプリケーション初期化
 * @details ボードとアプリケーションの各モジュールを初期化する。
 * @return 実行環境へ返す終了コード
 * ================================================================= */
int App_Init(void) {
```

- `@brief`は、関数の主な提供機能を短い動詞・名詞で表す。
- 引数がある場合だけ`@param[in]/[out]`を記載する。
- 戻り値がある場合は`@return`を記載する。
- 呼び出し条件、単位、安全動作、戻らない条件などが重要な場合だけ`@details`や`@note`、`@attention`を追加する。
- 関数内部の処理コメントにはDoxygen形式を使わない。
- `static`関数も、他の関数と同じ形式で記載する。

関数内部では、必要な箇所だけ通常コメントを使用し、対象となる文の直前に同じインデントで配置します。関数内部の行末コメントや61桁目への位置揃えは使用しません。

```c
/* センサー電源とI2C周辺機器の初期化を安定させる時間を確保する。 */
TimeControlDelayMs(10U);
```

次のように、明らかな代入やループの各行へコメントを付ける必要はありません。

```c
/* 明らかな初期値代入にはコメントを付けない。 */
snapshot.valid = false;
```

## include

`#include`の説明はDoxygen形式にせず、インクルード行の末尾に1行の通常コメントを付けます。
複数の`#include`は空行を挟まず連続して記載し、コメントの開始位置を揃えます。

```c
#include "mcu.h"                            /* ML63Q2557のレジスタ定義 */
#include "PlantDoctorConfig.h"              /* 周期処理とハードウェア待ち時間の設定 */
#include "SensorManager.h"                  /* センサー取得APIとスナップショット型 */
```

コメントには、ヘッダの提供元または用途を記載します。コード部分が60桁以内なら、コメントを同じ行の61桁目から記載します。

## コメント位置と行幅

- 通常のCコードは、120桁以内であれば可読性のために改行しない。70～80桁程度での機械的な折り返しは行わない。
- 120桁を超える場合だけ、意味の区切りが分かる位置で改行し、継続行は一段インデントする。
- 関数外の`#include`、関数宣言、`extern`、ファイルスコープ変数などの行末コメントは、コメント開始位置を61桁目に揃える。
- 関数内部の通常コメントは、説明対象の文の直前に同じインデントで置く。関数内部では行末コメントと61桁目への位置揃えを使用しない。
- コメントを除いたコード部分が60桁を超える場合は、行末コメントを置かず、通常コメントを直前の行へ移す。
- 関数宣言でも、コメントを除いた宣言部が60桁以内ならコメントを61桁目に揃える。宣言部が60桁を超え、宣言とコメントを合わせて120桁以内の場合だけは、1行での可読性を優先してコメントの前に半角スペースを1つ置く。
- 複数行のファイルスコープ変数コメントは、従来どおり宣言直前の`/**< ... */`形式とする。
- `#endif /* ... */`のインクルードガードコメントは、ガードの対応を示す構文上のコメントとして扱い、位置揃えの対象外とする。

## マクロ定義

連続するオブジェクト形式の`#define`は、マクロ名の次に空白を入れ、定義値の開始位置を行頭から44桁目に揃えます。
マクロ名が長く44桁目までに収まらない場合は、名前の直後に空白を1つ置きます。揃える範囲は
空行または別のプリプロセッサディレクティブまでの連続ブロックです。関数形式マクロと複数行
マクロは対象外とします。

```c
#define PLANT_DOCTOR_TICK_MS               (10U)
#define PLANT_DOCTOR_LED_BLINK_TICKS       (100U)
#define PLANT_DOCTOR_LCD_TIMEOUT_LOOPS     (4800000UL)
```

## 外部変数

`extern`変数は、宣言行の末尾に簡易的なDoxygenコメントを1行で記載します。

```c
extern volatile uint32_t g_command_sequence;               /**< 他モジュールが所有する最終sequence */
```

実体の定義場所や所有者が重要な場合は、短く補足します。

```c
extern volatile uint32_t g_command_sequence;               /**< アプリケーションが管理する最終sequence */
```

## 内部変数

`static`変数は、宣言位置によってコメント形式を分けます。

- 関数内の内部変数は、宣言直前に同じインデントの通常コメントを付ける。
- ファイルスコープの内部変数は、宣言行末に簡易的なDoxygenコメントを付ける。

```c
/* 次回出力するLEDレベル */
static bool level = false;                                  /**< 次回出力するLEDレベル */
```

ファイルスコープの配列など、宣言が複数行になる内部変数は、宣言の前の行へ`/**< ... */`形式のコメントを置きます。

```c
/**< センサー診断で表示するページ列 */
static const int16_t control_test_sequence[] = {
    CONTROL_TEST_CENTER,
    CONTROL_TEST_MINIMUM,
    CONTROL_TEST_MAXIMUM,
};
```

### 内部constの配置

`static const`変数は、原則として関数の外側、ファイルスコープへ置きます。モジュール内の定数・テーブルとしてまとめて確認できるようにするためです。

```c
/* モジュール定数 */
/**< センサー診断で表示するページ列 */
static const int16_t control_test_sequence[] = {
    CONTROL_TEST_CENTER,
    CONTROL_TEST_MINIMUM,
    CONTROL_TEST_MAXIMUM,
};
```

内部の可変状態は、これまでどおり使用範囲が最小になる場所へ置きます。関数専用の状態は関数内、複数の関数で共有する状態はファイルスコープとします。

ファイルスコープの`static const`は、同じ`.c`ファイル内からだけ参照でき、他のファイルへ公開されません。複数のコンポーネントで共有する定数は、必要に応じて共有ヘッダへ定義します。

## 関数宣言

関数宣言はDoxygen形式にせず、宣言行の末尾に1行の通常コメントを付けます。

```c
int app_main(void); /* ファームウェアアプリケーション初期化 */
```

引数を含む宣言も、コメントを含めて120桁以内なら1行にまとめます。宣言部が60桁以内なら、通常どおりコメントを61桁目に揃えます。

```c
static void acoustic_write_u16_le(uint8_t *output, uint16_t value); /* 16 bit LE書込 */
```

関数の詳しい説明は、実装側のDoxygenコメントへ記載します。

関数名と引数リストの開き括弧の間にはスペースを入れません。

```c
static void status_led_toggle(void) {
    status_led_toggle();
}
```

次のような書式は使用しません。

```c
static void status_led_toggle(void)
```

## 中括弧

関数、`if`、`for`、`while`、`switch`などの中括弧はK&Rスタイルとします。開き中括弧は宣言・制御文と同じ行に置きます。

```c
static void led_toggle(void) {
    if (Board_IsPowerHeld()) {
        LedControl_Toggle(LED_CONTROL_1);
    } else {
        error_loop();
    }
}
```

`else`、`else if`、`while`（`do`-`while`の場合）は、直前の閉じ中括弧と同じ行に置きます。

```c
do {
    led_toggle();
} while (running);
```

配列初期化子の中括弧も、宣言と同じ行から開始します。

```c
static const uint16_t limits[] = {
    0U,
    100U,
}; /**< 出力制限値 */
```

## 関数内部の変数

永続化しないローカル変数は、処理の理解に必要な場合だけ通常コメントを付けます。

```c
/* センサー初期化APIの戻り値 */
bool initialized = SensorManager_Init();
/* 現在のセンサー値 */
PLANT_SENSOR_SNAPSHOT snapshot;
```

型名や変数名だけで役割が明らかな場合は、コメントを省略します。

## コメントの内容

次のような、実装意図や安全条件に関わる内容を優先してコメントします。

- 複数のプロセッサまたはコンポーネント間の責務分担
- センサー・アクチュエータ通信の意味、送信順序、完了条件
- 起動待ち、周期処理、タイムアウト
- 緊急停止、フェイルセーフ、出力制限
- GPIOの論理、PWM周波数、エンコーダ分解能などのハードウェア依存事項
- 未実装機能や、実機確認が必要な箇所

単なる制御構文や代入の説明、コードと矛盾する古い説明は残さないでください。

## 生成コードとの境界

MCUベンダーのSDKまたはIDEが生成する領域は、ユーザー処理やコメントを直接書き込まず、
ユーザーソース配下から利用します。ML63Q2557プロジェクトでは、次が該当します。

```text
firmware/ml63q2557/CommonFiles/
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/startup_ML63Q25x7.c
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/system_ML63Q25x7.*
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/ML63Q25x7.*
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/NmiHandler.c
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/codeoption*
firmware/ml63q2557/PlantDoctorWorkspace/PlantDoctor/*.ld
```

ユーザーコードの入口やアプリケーション処理は、`PlantDoctor/`配下の各ユーザーソース
ディレクトリへ配置します。ドライバサンプル由来のコードも、由来が明確な場合は生成コードと
同様に扱い、必要な修正はユーザー側のラッパーに記載します。

## 作成時の確認項目

- [ ] ファイルヘッダは`=`デコレーション付きのDoxygen形式になっている。
- [ ] `@brief`は説明口調ではなく、機能を示す短い動詞・名詞になっている。
- [ ] 関数実装には必要な`@details`、`@param`、`@return`だけを付けている。
- [ ] `#include`と関数宣言は1行の通常コメントになっている。
- [ ] ML63Q2557ユーザーコードは標準Cの固定幅型、`bool`、`static`、`extern`を使用している。
- [ ] MCU・周辺機器API境界とwire formatの型は、それぞれの提供元・仕様を維持している。
- [ ] 通常のCコードを、120桁以内で機械的に折り返していない。
- [ ] 関数外の行末コメントは61桁目から始まっている。
- [ ] 関数宣言は、コメントを含めて120桁以内なら1行にまとめている。
- [ ] コード部分が60桁を超える行は、コメントを直前の行へ移している。
- [ ] 連続するオブジェクト形式の`#define`は、定義値の開始位置を揃えている。
- [ ] ファイルヘッダの終了行の直後に空行を置いていない。
- [ ] `#include`同士の間に空行を置かず、コメントの開始位置を揃えている。
- [ ] 関数名と引数リストの`()`の間にスペースを入れていない。
- [ ] `extern`とファイルスコープの内部変数は簡易Doxygenコメントになっている。
- [ ] 関数内の内部変数は、同じインデントの直前行コメントで説明されている。
- [ ] 複数行の内部変数は、宣言前の行に`/**< ... */`形式のコメントを置いている。
- [ ] `static const`変数は、原則としてファイルスコープに配置している。
- [ ] 中括弧はK&Rスタイルで、開き中括弧を宣言・制御文と同じ行に置いている。
- [ ] 関数内部のコメントは必要最低限で、Doxygen形式を使っていない。
- [ ] 生成コードを直接変更していない。
- [ ] コメントの単位・対象プロセッサ・通信仕様・安全条件が実装と一致している。
